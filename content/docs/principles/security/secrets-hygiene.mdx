<AIInstruction>
Never write secrets into source files, configuration templates, commit messages, tickets, chat logs, or log output — not even temporary ones, not even in a private repository. Always read secrets from a vault or environment injection at runtime, and rotate immediately if a secret has touched a repo. If you find a secret in code, a paste, or a log, stop and report it to a human with its exact location.
</AIInstruction>

<Severity level="critical" />

## Definition

A secret is any credential whose disclosure breaks a security boundary: API keys, tokens, passwords, private keys, connection strings. Code and its history are broadcast media — a secret committed once is copied to every clone, CI log, and archive, and rewriting history does not un-leak it. Hygiene means secrets exist only in vaults and runtime injection, are scoped and rotated, and are treated as compromised the moment they touch anything someone else can read.

## When to use

- Writing any script, service, or CI job that authenticates to something.
- Committing configuration, infrastructure code, or container images — the classic leak sites.
- Debugging and logging: the moment you print request headers or environments.
- Handing an agent or automation credentials to work on your behalf.

## When NOT to use

- Public keys and other identifiers designed to be shared — mislabeling them as secrets creates alert fatigue, which hides the real ones.
- Test fixtures with structurally fake values that real systems reject — obviously invalid example keys are safe and useful.
- Encrypted secrets committed to a repo where the decryption key is injected by CI from a vault — an accepted practice in some teams, defensible only while the key truly never enters git.

## Anti-pattern

- A connection string with its password committed in an example env file — example files get real values pasted into them.
- A token pasted into a ticket comment "just for the sprint".
- The deploy key baked into the base image "because builds were failing".
- Logging full request headers and environments on every error path.
- Planning to revoke a leaked key "later this week" instead of now.
- Treating a private repo as a safe place: private repos get cloned, mirrored, and remembered by ex-employees.

## Code example

Wrong — the secret lives in the repo:

```bash
# The .env file was committed "temporarily" during a deploy fire:
#   DATABASE_URL=postgres://svc:realpassword@prod-db.internal:5432/billing
# One push later: every clone, CI log, and mirror of the repo holds it forever.
git rm .env && git commit -m "remove env"   # pointless — history still has it
```

Right — the repo references names; the runtime provides values:

```bash
# Repo contains only the reference; vault or CI injects the real value.
./deploy.sh                      # reads DATABASE_URL from the environment

# Defense in depth around the secret:
# - pre-commit secrets scanner: commit fails BEFORE history exists
# - vault issues short-lived DB credentials per deploy, not per quarter
# - if a leak is suspected: rotate FIRST, then investigate how it leaked
```

## Technical enforcement

<Enforcement>
Hygiene survives only as tooling:

- **Pre-commit and server-side secret scanning** on every push — including on history rewrites, which are themselves a red flag worth alerting on.
- **Vault plus short-lived credentials**: secrets issued per job per run (OIDC federation to cloud roles instead of long-lived keys), so a leaked token ages out in minutes.
- **CI masking and scoping**: secrets masked in logs and never exposed to pull requests from forks.
- **A rehearsed rotation runbook**: revoking and rotating one credential class end to end, practiced before it is needed.
- **What prevents vs. detects**: per-run federated credentials prevent leaks from mattering — the leaked thing expires before anyone uses it; scanners detect the leak after the fact. Detection tells you prevention was imperfect; do not ship the first without planning the second.
</Enforcement>

## Real-world case

<RealCase>
Scenario (ilustratif): an engineer commits a working access token into a repository — inside a code sample, a config file, or a late-night fix — and automated scrapers find it within minutes to days. Because git history is effectively append-only, deleting the file leaves the token in every clone and archive that already exists; the only real remediation is revocation and rotation, under time pressure, with the attacker already holding a valid credential. A similar real-world event — a stolen npm token used in 2018 to publish malicious versions of an official package — should be verified against primary sources before citing further (verification: perlu). The lesson holds either way: treat any secret that has touched a repo as compromised, and make rotation so routine that it is boring. No URL is cited because this case is illustrative, not a specific verified incident.
</RealCase>

## Tension and trade-off

- **Hygiene vs. KISS**: vault wiring, scopes, and rotation add real setup complexity; the boring minimal version — environment injection from a vault — beats the elaborate one nobody maintains.
- **Secrets vs. Observability-First**: debugging wants the exact failing credential and header values; mask by default and unmask only through a controlled, audited path.
- **Aggressive rotation vs. graceful degradation**: credentials that expire under a running service can take it down mid-flight; rotation needs overlap windows or live reload, and a failed rotation should fail loudly, not silently.

## Related principles

- [Secure by Default](/docs/principles/security/secure-by-default) — tools that demand secrets only at runtime, never in files.
