<AIInstruction>
Beri setiap penyeberangan boundary — HTTP request, pesan queue, webhook, baris database, environment variable — sebuah schema yang dideklarasikan, dan validasilah di titik masuk. Perlakukan setiap asumsi yang tak tertulis (urutan field, nullability, satuan, timezone, encoding) sebagai defect yang menunggu jadwal untuk dikerjakan. Jika Anda mengonsumsi output sebuah producer, minta schema-nya secara tertulis di kode dan test, bukan lewat pengetahuan lisan.
</AIInstruction>

<Severity level="important" />

## Definisi

Setiap data yang menyeberangi boundary proses, service, atau kepemilikan membawa sebuah contract eksplisit: schema yang dimiliki dan divalidasi oleh sisi penerima. Eksplisit berarti dapat diperiksa mesin — sebuah type di shared package, sebuah JSON Schema, sebuah definisi protobuf — bukan halaman wiki. Contract implisit (asumsi tentang urutan, format, default) tetaplah contract; hanya saja ia tak tersaksi, tak teruji, dan baru ditemukan di production.

## Kapan pakai

- Panggilan service-to-service dan client-server; webhook serta callback pihak ketiga.
- Event stream dan queue tempat producer dan consumer deploy secara independen.
- Membaca tabel, ekspor, atau file milik tim lain — termasuk output migration sendiri di masa lalu.
- Mengonsumsi configuration dan environment variable saat startup.

## Kapan TIDAK pakai

- Panggilan hot in-process yang sudah diperiksa compiler — memvalidasi ulang di sana murni overhead; validasilah di boundary, lalu percayai type di dalamnya.
- Skrip sekali pakai atas file yang ditulis dan dibaca dalam satu proses yang sama.
- Ketika sebuah format masih aktif diciptakan dalam prototype — tetapi promosikan ia menjadi schema sebelum consumer kedua muncul.

## Anti-pattern

- Positional unpacking field JSON — mengandalkan urutan yang tidak terdokumentasi.
- "Producer selalu mengirim cents" atau "timestamp-nya selalu UTC" — tidak tertulis di mana pun, tidak diperiksa di mana pun.
- Copy-paste sebuah type ke dalam consumer alih-alih membagikan package schema berversi.
- Schema drift: producer mengembangkan payload, tidak ada diff yang gagal, dan asumsi consumer kedaluwarsa secara diam-diam.

## Contoh kode

Salah — contract-nya hidup dalam asumsi yang tak terdokumentasi:

```ts
// "getJob selalu mengembalikan field sesuai urutan penyisipan" — tak pernah ada yang menulisnya, di mana pun, kapan pun
const [id, status] = Object.values(await getJob(jobId)) as [string, string];
if (status === 'done') markComplete(id);
```

Benar — field bernama, divalidasi di boundary:

```ts
const Job = z.object({
  id: z.string(),
  status: z.enum(['queued', 'running', 'done', 'failed']),
});
const job = Job.parse(await getJob(jobId)); // tak bergantung urutan, key tak dikenal ditolak
if (job.status === 'done') markComplete(job.id);
```

## Penegakan teknis

<Enforcement>
Prinsip ini ditegakkan di tempat data masuk, bukan di tempat ia didiskusikan:

- **Validasi schema di setiap boundary** (zod, JSON Schema, protobuf/Avro): parse, jangan periksa manual; tolak key tak dikenal; fail fast di titik masuk.
- **Consumer-driven contract tests** (Pact): CI producer berjalan melawan ekspektasi consumer nyata, menangkap drift sebelum deploy.
- **OpenAPI spec sebagai source of truth di CI**: spec ada, cocok dengan implementasi lewat round-trip test, dan diff setiap PR diklasifikasikan.
- **Schema registry dengan compatibility check** untuk event: producer tidak bisa merge perubahan shape yang breaking.
- **Package contract bersama**, berversi dan dipublikasikan — satu definisi, bukan N salinan.
</Enforcement>

## Kasus nyata

<RealCase>
Sebuah consumer membangun mapping-nya di atas urutan field response JSON milik sebuah producer — tak pernah terdokumentasi, hanya teramati. Producer kemudian memperbaiki apa yang dianggapnya bug sort yang tak berbahaya, mengubah urutan elemen. Logika positional si consumer lalu memetakan ID ke record yang salah, dan ketidakcocokan itu mengalir ke report di hilir selama berhari-hari sebelum sebuah reconciliation menandainya; tidak ada yang menghubungkan perbaikan sort yang "tak berbahaya" itu dengan mapping yang rusak. Schema ber-field-bernama akan mengurangi korupsi senyap berhari-hari itu menjadi sebuah contract test yang gagal di CI. (ilustratif — komposit dari mode kegagalan yang umum; verification: perlu)
</RealCase>

## Tensi dan trade-off

- **Biaya validasi vs. throughput**: mem-parse setiap pesan masuk memakan CPU pada volume tinggi; validasilah di boundary dan operkan data yang typed dan terpercaya ke dalam — bukan pemeriksaan berulang in-process.
- **Keketatan vs. toleransi**: Robustness Principle berargumen untuk menerima input yang tak sempurna; prinsip ini berargumen untuk menolak yang tak terdefinisi. Resolusinya: toleransi adalah pengecualian yang terdokumentasi dan ter-log di dalam contract — bukan dongeng turun-temurun.
- **Upacara schema vs. kecepatan**: menulis contract lebih dulu terasa lambat; itu tetap lebih murah daripada versi jam 3 pagi, dan consumer-driven test mengubahnya menjadi jaring pengaman, bukan paperwork.
