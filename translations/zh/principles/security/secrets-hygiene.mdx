<AIInstruction>
绝不把 secret 写进源码文件、配置模板、commit message、工单、聊天记录或日志输出——哪怕临时的，哪怕在私有 repo 里。始终在运行时从 vault 或环境注入读取 secret；一旦某个 secret 碰到过 repo，立即轮换。如果你在代码、paste 或日志里发现了 secret，停下来，带着它的准确位置上报给人。
</AIInstruction>

<Severity level="critical" />

## 定义

secret 是任何一旦泄露就击穿安全边界的凭证：API key、token、密码、private key、连接串。代码和它的历史是广播媒体——一个 secret 只要被 commit 过一次，就被复制到每一个 clone、CI 日志和归档里，重写历史也不能撤销泄露。卫生意味着：secret 只存在于 vault 和运行时注入中，有 scope、会轮换，并且在它碰到任何别人能读到的东西的那一刻起，就按已泄露处理。

## 何时使用

- 编写任何需要向什么东西做认证的脚本、service 或 CI job。
- commit 配置、基础设施代码或容器镜像——经典的泄漏地点。
- 调试与打日志：你打印 request header 或环境变量的那一刻。
- 把凭证交给 agent 或自动化，让它们代表你工作。

## 何时不该使用

- 公钥以及其他本就设计为共享的标识符——把它们误标为 secret 只会制造告警疲劳，反而淹没真正的警报。
- 使用结构性假值、会被真实系统拒绝的测试 fixture——明显无效的示例 key 既安全又有用。
- 加密后的 secret 提交进 repo、解密密钥由 CI 从 vault 注入——一些团队接受的做法，只有当密钥确实从不进入 git 时才站得住脚。

## 反模式

- 示例 env 文件里带着密码的连接串——示例文件迟早会被粘上真值。
- 「就这个 sprint 临时用一下」而粘进工单评论的 token。
- 「因为构建老失败」而烧进基础镜像的 deploy key。
- 每条错误路径都完整打印 request header 和环境变量。
- 打算「这周晚点再」撤销一把已泄漏的 key，而不是现在就做。
- 把私有 repo 当成安全的地方：私有 repo 会被 clone、被镜像、被前员工记住。

## 代码示例

错误示范——secret 活在 repo 里：

```bash
# .env 文件是在一次部署救火中「临时」commit 进来的：
#   DATABASE_URL=postgres://svc:realpassword@prod-db.internal:5432/billing
# 一次 push 之后：repo 的每个 clone、CI 日志、镜像都永久持有它。
git rm .env && git commit -m "remove env"   # 徒劳——历史里仍然有它
```

正确示范——repo 里只有名字，运行时提供值：

```bash
# repo 里只有引用；真实值由 vault 或 CI 注入。
./deploy.sh                      # 从环境变量读取 DATABASE_URL

# 围绕 secret 的纵深防御：
# - pre-commit secret 扫描器：在历史存在之前就让 commit 失败
# - vault 按每次部署签发短期 DB 凭证，而不是每季度一次
# - 一旦怀疑泄漏：先轮换，再调查它是怎么漏的
```

## 技术执法

<Enforcement>
卫生只有变成工具才能存活：

- **pre-commit 与服务端 secret 扫描**，覆盖每一次 push——也覆盖历史重写本身，那本身就是值得告警的可疑信号。
- **vault 加短期凭证**：每个 job、每次运行单独签发（用 OIDC federation 换取云 role，而非长期 key），泄漏的 token 几分钟后就过期作废。
- **CI 的掩码与作用域**：日志中的 secret 一律打码，且绝不暴露给来自 fork 的 pull request。
- **演练过的轮换 runbook**：端到端地撤销并轮换一整类凭证，在需要它之前就演练过。
- **预防 vs. 检测**：按次签发的联邦凭证让泄漏不再致命——被泄漏的东西在任何人用上它之前就已过期；扫描器在事后发现泄漏。检测告诉你预防并不完美；没把第二半规划好，就不要只上线第一半。
</Enforcement>

## 真实案例

<RealCase>
场景（ilustratif）：一位工程师把一枚可用的 access token commit 进了 repo——藏在一个代码示例里、一个配置文件里、或一次深夜修复里——自动化爬虫在几分钟到几天内找到它。因为 git 历史实际上是仅追加的，删除文件并不能把 token 从已经存在的每个 clone 和归档里抹掉；唯一真正的补救是撤销与轮换，而且是在攻击者已经握着有效凭证的时间压力下进行。一个相似的真实事件——2018 年一枚被窃取的 npm token 被用来发布某个官方 package 的恶意版本——在进一步引用前应先对照一手来源核实（verification: perlu）。无论哪种情况，教训都成立：把任何碰到过 repo 的 secret 当作已泄露处理，并把轮换做成例行公事，无聊到没有人再谈论它。此处未引用 URL，因为这个案例是示意性的，不是某个经过核实的具体事件。
</RealCase>

## 张力与权衡

- **卫生 vs. 保持简单**：vault 接线、scope、轮换都带来真实的搭建复杂度；那个无聊的极简版——从 vault 做环境注入——胜过没人维护的精雕细琢版。
- **secret vs. 可观测性优先**：调试时想要精确出错的凭证和 header 值；默认打码，只通过受控、留痕的路径解除。
- **激进轮换 vs. 优雅降级**：在运行中的 service 里过期的凭证可能让它在半路倒下；轮换需要重叠窗口或热重载，而失败的轮换应该大声失败，而不是静默。

## 相关原则

- [最小权限 · Least Authority](/zh/docs/principles/security/least-authority)——一枚泄漏的、带 scope 的短期凭证是一次割伤，不是一次截肢。
- [默认即安全 · Secure by Default](/zh/docs/principles/security/secure-by-default)——工具只在运行时索要 secret，绝不在文件里。
- [供应链审查 · Supply Chain Vetting](/zh/docs/principles/security/supply-chain-vetting)——泄漏的 CI token 正是恶意 package 发布的原料。
- [故障安全默认 · Fail-Safe Defaults](/zh/docs/principles/security/fail-safe-defaults)——secret 缺失时 fail-closed，而不是回退到 repo 里那份。
- [可观测性优先 · Observability First](/zh/docs/principles/reliability/observability-first)——日志要丰富到能调试，也要盲到守得住。
- [仅追加日志 · Append-Only Logs](/zh/docs/principles/data/append-only-logs)——为什么历史从不遗忘，为什么轮换是唯一真正的修复。
