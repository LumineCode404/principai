<AIInstruction>
Treat every retry as a bet that pays off only when the failure is transient and the callee has spare capacity. Use exponential backoff with full jitter, cap attempts per request, and enforce a global budget on total retry volume — when the budget is spent, fail fast and surface the error. Never ship a retry loop that lacks all three limits.
</AIInstruction>

<Severity level="important" />

## Definition

A retry budget is a hard, measured limit on how much extra load retries may add — for example, retries may be at most a fixed small share of all requests — combined with exponential backoff and jitter so attempts spread over time. Retries are hope converted into load; when the callee is already failing, that load lands on the weakest component and converts a blip into an outage. The budget is what keeps hope affordable.

## When to use

- Any client of a remote dependency (HTTP, RPC, database, broker) with timeout-capable calls.
- Event-driven consumers that requeue or re-deliver failed messages.
- Batch pipelines that re-run failed items.
- SDKs and libraries others will embed — their retry defaults become someone else's architecture (see Hyrum's Law).

## When NOT to use

- Non-idempotent operations without a key — retrying a payment without idempotency is a correctness bug, not resilience.
- Latency-sensitive requests whose caller already left — retrying after the user abandoned the page is pure load with no beneficiary.
- Client errors and business rejections — retrying a validation error is a loop with extra steps.
- Strictly ordered work where a delayed retry would apply state out of order.

## Anti-pattern

- Immediate retries, fixed count, no jitter — every client hammers in lockstep, exactly when the target is worst off.
- Nested retries at every layer: client, gateway, service, and database each retry three times; the multipliers compound.
- Retrying harder precisely when the dependency is overloaded — amplifying the very signal that should trigger shedding.
- Retry policy decided per call site by each developer independently, with no global view.

## Code example

Wrong — synchronized, unbounded retry:

```python
for attempt in range(3):
    try:
        return search_client.query(q)      # instant retries, in lockstep everywhere
    except Timeout:
        continue                           # no jitter, no budget, no deadline
raise SearchUnavailable(q)                 # after hammering an already-dying service
```

Right — backoff, jitter, deadline, and a global cap:

```python
def search(q, deadline):
    for attempt in range(3):
        if monotonic() >= deadline:
            raise SearchUnavailable(q)                       # caller left: stop retrying
        sleep(random.uniform(0, 0.1 * 2 ** attempt))         # exponential + full jitter
        try:
            return search_client.query(q, timeout=0.2)       # hard timeout per attempt
        except (Timeout, Unavailable):
            continue
    raise SearchUnavailable(q)
```

## Technical enforcement

<Enforcement>
Retries are a system property, not a per-developer preference — enforce them centrally:

- **Client library defaults**: backoff, jitter, attempt cap, and retry-on status list ship in the standard client; bare retry helpers are rejected in code review.
- **Retry budgets at the caller**: a token-bucket or circuit-breaker allows at most 1 retry per N requests; when the budget is empty, requests fail fast with a loud error.
- **Server-side protection**: the callee distinguishes and rejects excess retry traffic (busy responses with retry-after guidance) so callers learn instead of hammering.
- **Deadline propagation**: every request carries its remaining patience; nested retries cannot multiply beyond the caller's deadline.
- **Tests**: killing a dependency in staging must produce bounded, measurable extra load — visible as a bump, not a storm.
</Enforcement>

## Real-world case

<RealCase>
(ilustratif) A downstream dependency blips for sixty seconds during a deploy. Every client retries immediately — three attempts, no jitter — and retry traffic exceeds normal traffic right as the dependency comes back up. The recovering service spends the next forty minutes processing a synchronized queue of retries instead of user requests; the monitoring graph shows the caller failing long after the dependency was healthy. Backoff with jitter plus a hard budget would have reduced a self-inflicted partial outage to a brief bump in error rate. (verification: perlu — retry-storm incidents are described in public postmortems; belum digali — verify specific sources before citing any of them.)
</RealCase>

## Tension and trade-off

- **Retry Budget vs. latency SLOs**: aggressive retries buy milliseconds of availability in good times and cost minutes of outage in bad times; budget for the bad times.
- **Retry Budget vs. Idempotency**: retrying is only safe where idempotency already holds; make the operation safe before making the retry automatic.
- **Weigh against Fail-Visible**: budget-exhausted failures must surface as loud errors — a framework that silently drops them converts unavailability into data loss.
