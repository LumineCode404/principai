<AIInstruction>
Buat business logic bergantung pada interface yang dimilikinya sendiri, dan dorong SDK, driver, serta client konkret ke lapisan terluar. Jangan pernah meng-import package vendor langsung dari domain code — definisikan port-nya lebih dulu, lalu adaptasikan vendor ke port itu. Ketika test butuh credentials vendor yang live untuk menjalankan core logic, perlakukan itu sebagai sinyal untuk meng-invert dependency tersebut.
</AIInstruction>

<Severity level="advisory" />

## Definisi

Policy di level tinggi — aturan billing, logic booking, apa pun yang dibayar bisnis untuk itu — tidak boleh bergantung pada detail level rendah seperti payment SDK, database driver, atau HTTP client. Kedua sisi bergantung pada sebuah abstraction, dan yang krusial: abstraction itu dimiliki pihak level tinggi — ia berbicara dalam bahasa domain, bukan bahasa vendor. Detail kemudian menancap ke core, sehingga menukar atau mem-fake infrastructure berhenti menjadi penulisan ulang.

## Kapan pakai

- Core domain logic yang harus bisa dites tanpa jaringan, disk, atau akun vendor.
- Infrastructure dengan peluang penggantian yang realistis: payment provider, storage backend, mail relay, message broker.
- Perancangan library: konsumen menulis kode melawan surface-nya, bukan bagian internalnya.
- Target deployment yang beragam — cloud versus on-prem, provider regional yang berbeda-beda.

## Kapan TIDAK pakai

- Wrapper yang dibangun "just in case" di sekeliling satu SDK tanpa implementasi kedua yang terlihat — abstraction spekulatif.
- Kode infrastructure tipis yang tugas utamanya memang berbicara dengan satu vendor — adapter yang hanya mengganti nama API vendor menambah gesekan, bukan kebebasan.
- Skrip dan prototype berumur pendek yang biaya penulisan ulangnya mendekati nol.
- Membungkus teknologi yang justru kekuatan penuhnya adalah inti persoalannya, seperti query language sebuah search engine — abstraction-nya akan bocor.

## Anti-pattern

- `BillingService` meng-import payment SDK secara langsung: policy yang dilas ke satu vendor.
- "Abstraction" yang merupakan cermin 1:1 dari SDK vendor, termasuk error model-nya.
- Interface yang didefinisikan di dalam package wrapper vendor — domain kini bergantung pada detail yang sedang ia hindari.
- Test suite yang mensyaratkan credentials pihak ketiga yang live karena tidak ada seam untuk di-fake.

## Contoh kode

Salah — domain meng-import vendor; setiap perubahan provider adalah operasi di jantung core:

```ts
// billing/billing-service.ts
import Stripe from 'stripe';
export class BillingService {
  async charge(cart: Cart) {
    const s = new Stripe(process.env.STRIPE_KEY!);
    const charge = await s.charges.create({ amount: cart.totalCents });
    return charge.id; // domain kini tahu bentuk response Stripe
  }
}
```

Benar — domain memiliki port-nya; vendor menjadi detail yang bisa diganti:

```ts
// billing/payment-gateway.ts — bahasa domain, file domain
export interface PaymentGateway { charge(cart: Cart): Promise<Receipt>; }
// infra/stripe-gateway.ts — satu-satunya file yang tahu Stripe ada
export const stripeGateway = (key: string): PaymentGateway => ({
  async charge(cart) {
    const s = new Stripe(key);
    return toReceipt(await s.charges.create({ amount: cart.totalCents }));
  },
});
```

## Penegakan teknis

<Enforcement>
Prinsip ini ditegakkan oleh build, bukan oleh niat:

- **Aturan import boundary di CI** (dependency-cruiser, eslint-plugin-boundaries): folder domain tidak boleh meng-import infrastructure atau package vendor — pelanggarannya menggagalkan build.
- **Architecture test**: aturan bergaya ts-arch atau ArchUnit yang menegaskan bahwa port hidup di lapisan domain dan implementasinya di luarnya.
- **Bukti seam test**: unit test core logic berjalan melawan fake gateway in-memory, tanpa jaringan dan tanpa credentials vendor — jika tidak bisa, dependency itu belum ter-invert.
- **Checklist review**: adakah file di bawah domain atau core yang meng-import SDK? Jika ya, berhenti dan definisikan port-nya lebih dulu.
</Enforcement>

## Kasus nyata

<RealCase>
Sebuah produk subscription meng-hard-wire core billing-nya ke SDK satu payment provider — charge, refund, retry, sampai error handling pun ditulis dalam istilah vendor. Ketika negosiasi ulang kontrak membuat penggantian provider menjadi keharusan, "integrasi" itu berubah menjadi penulisan ulang berbulan-bulan: konsep vendor telah menjadi penyangga di dalam aturan bisnis inti. Sebuah port gateway milik domain dengan adapter per provider akan mengurangi pergantian itu dari penulisan ulang menjadi proyek adapter plus sebuah data migration yang cermat. (ilustratif — komposit dari mode kegagalan yang umum; verification: perlu)
</RealCase>

## Tensi dan trade-off

- **Dependency Inversion vs. YAGNI**: setiap port dan adapter adalah indirection yang harus dibaca seseorang. Perkenalkan seam saat implementasi kedua masuk akal atau saat testing menuntut isolasi — bukan untuk setiap import secara default.
- **Dependency Inversion vs. KISS**: wrapper pass-through di sekeliling satu SDK menambah lapisan tanpa kemampuan baru; timbang biaya menukar nanti melawan biaya memahami sekarang.
- **Port di mana-mana vs. Least Astonishment**: terlalu banyak interface berimplementasi tunggal menjadikan codebase sebuah labirin. Jaga port tetap sedikit, kecil, dan dinamai dalam bahasa domain.

## Prinsip terkait

- [Single Responsibility](/id/docs/principles/architecture/single-responsibility) — inversion bekerja paling baik ketika port-nya sendiri hanya punya satu alasan untuk berubah.
- [Explicit Contracts](/id/docs/principles/api/explicit-contracts) — sebuah port adalah contract: deklarasikan dan validasi apa pun yang menyeberanginya.
- [Gall's Law](/id/docs/principles/architecture/gall-law) — ekstrak abstraction saat kebutuhan kedua muncul, bukan sebelumnya.
- [YAGNI](/id/docs/principles/design/yagni) — pemberat melawan port spekulatif.
- [KISS](/id/docs/principles/design/kiss) — indirection adalah biaya; bayar hanya di tempat ia membeli decoupling.
