<AIInstruction>
Sebelum deduplikasi, pastikan salinan-salinannya berubah karena alasan yang sama dan akan berubah bersama-sama. Jangan mengekstrak shared abstraction dari kurang dari tiga consumer nyata yang independen. Perlakukan duplikasi yang disengaja antar tim yang deploy secara independen sebagai keputusan decoupling, bukan defect. Jika sebuah abstraction terpadu sudah menjadi medan pertempuran, pecahkan kembali sepanjang garis alasan perubahan masing-masing.
</AIInstruction>

<Severity level="advisory" />

## Definisi

DRY mengatakan setiap knowledge harus punya satu representasi otoritatif — tetapi satuan knowledge adalah alasan perubahan, bukan teks di layar. Duplikasi FAKTA itu buruk: satu business rule yang dinyatakan dua kali cepat atau lambat akan diedit sekali dan mengirim bug. Duplikasi KEBETULAN tidak masalah: dua blok yang tampak sama tetapi berubah karena alasan berbeda harus tetap terpisah, karena menggabungkannya meng-couple hal-hal yang harus berevolusi terpisah.

## Kapan pakai

- Sebuah konstanta, formula, atau business rule muncul di beberapa tempat yang harus saling setuju: tarif pajak, batas retry, makna status.
- Sebuah bug diperbaiki di satu salinan dan ditemukan lagi di salinan lain.
- Mengekstrak shared code begitu setidaknya dua — lebih baik tiga — consumer independen sudah ada dan seorang owner bernama bersedia memeliharanya.
- Mengonsolidasikan modul di dalam satu batas yang dimiliki satu tim dari ujung ke ujung.

## Kapan TIDAK pakai

- Dua tim menduplikasi client kecil agar tetap bisa deploy secara independen — salinan itu adalah harga decoupling (lihat Conway's Law).
- Blok yang sekadar tampak mirip tetapi berubah karena alasan berbeda — itu kebetulan, bukan fakta.
- Kurang dari tiga kemunculan — ekstrak pada yang ketiga, bukan yang pertama.
- Sharing yang akan melintasi batas kepemilikan tanpa owner yang bersedia memelihara hasilnya.

## Anti-pattern

- Satu helper "terpadu" dengan flag untuk setiap perbedaan tiap consumer — kini lebih kompleks daripada semua salinan yang digabungkan.
- Shared library tanpa owner, diberi versi dengan harapan belaka.
- Deduplikasi hanya dengan tool kemiripan teks, tanpa pertimbangan mengapa setiap salinan ada.
- Mempertahankan abstraction yang salah karena menghapusnya berarti mengakui bahwa ekstraksinya terlalu dini.

## Contoh kode

Salah — satu helper untuk dua API yang hanya tampak mirip:

```ts
// Request helper "terpadu": setiap opsi ada hanya untuk tepat satu tim
export function request(path: string, opts: ReqOpts) {
  if (opts.oauth) { /* khusus payments: token refresh */ }
  if (opts.retryBudget) { /* khusus search: backoff policy */ }
  if (opts.noRedirect) { /* khusus payments: syarat auditor */ }
  return fetch(base(opts.env) + path, opts);
}
```

Benar — dua client, dua kebijakan; duplikasinya disengaja:

```ts
// Payments: token per panggilan, redirect dilarang, tanpa client retry (idempotency di upstream)
export async function payRequest(path: string, init: RequestInit) {
  const token = await paymentsToken();
  return fetch(PAY_BASE + path, { ...init, redirect: "error",
    headers: { ...init.headers, Authorization: token } });
}

// Search: stateless, murah, aman untuk retry dengan budget
export function search(q: string) {
  return withRetry(() => fetch(SEARCH_BASE + "?q=" + encodeURIComponent(q)), 3);
}
```

## Penegakan teknis

<Enforcement>
Pertimbangan adalah alatnya, tetapi tooling menjaga pertimbangan itu tetap jujur:

- **Deteksi copy-paste sebagai sinyal, bukan gerbang**: jalankan jscpd / PMD CPD di CI dan pantau tren angkanya; manusia yang memutuskan apakah setiap temuan adalah fakta atau kebetulan.
- **Rule of three di template PR**: mengekstrak shared code mengharuskan menyebutkan dua consumer independen yang sudah ada selain milik penulis, plus satu owner bernama.
- **ADR untuk shared library**: decision record singkat yang menyatakan apa yang disatukan oleh abstraction itu, siapa pemiliknya, dan bagaimana versinya (lihat Explicit Contracts).
- **Metrik coupling**: lacak inbound dependency pada modul bersama; modul yang dikonsumsi tim dengan ritme release berbeda membutuhkan kebijakan versioning eksplisit atau pemecahan.
</Enforcement>

## Kasus nyata

<RealCase>
Dua tim — payments dan search — masing-masing punya HTTP client kecil. Seorang engineer berniat baik menyatukan keduanya menjadi satu request helper dengan opsi yang mencakup keduanya. Selama setahun berikutnya, dua API upstream itu berevolusi terpisah: model auth, semantik retry, dan error payload yang berbeda. Setiap perubahan pada helper merusak satu tim; setiap perbaikan menambah flag; file itu menumpuk opsi yang tak bisa diuji tuntas oleh siapa pun, dan PR di atasnya berubah menjadi negosiasi lintas tim. Kedua tim mulai mengakalinya dengan wrapper lokal. Helper itu akhirnya dipecah kembali menjadi dua client yang fokus, masing-masing lebih kecil daripada versi bersamanya, dan velocity pulih — duplikasi tidak pernah menjadi masalahnya; penyatuan yang terlalu dini itulah masalahnya. (ilustratif — komposit dari mode kegagalan umum, bukan insiden bernama; verification: perlu)
</RealCase>

## Tensi dan trade-off

- **DRY vs decoupling**: dua tim menduplikasi client dua ratus baris demi tetap bisa deploy secara independen bisa jadi benar — versi bersama meng-couple release train mereka selamanya. Di tempat Conway's Law menggambar batas organisasi yang nyata, duplikasi kode sering kali adalah refleksi yang benar dari batas itu.
- **DRY vs abstraction prematur**: abstraction yang diekstrak dari satu contoh mengodekan tebakan hari ini tentang variasi esok; ketika kenyataan menyimpang, setiap caller melawannya, dan abstraction yang salah lebih mahal untuk dibongkar daripada duplikasi yang ia gantikan. Rule of three ada untuk memaksa setidaknya dua titik data nyata sebelum menyatukan apa pun.
- **Fakta vs kebetulan — uji operasionalnya**: duplikasi FAKTA (satu rule yang harus berubah serentak: sebuah tarif, sebuah status code, sebuah formula) cepat atau lambat mengirim bug di mana satu salinan terlewat — satukan. Duplikasi KEBETULAN (tampak mirip, berubah karena alasan berbeda) membeli evolusi independen — biarkan, dan tinggalkan comment yang mengatakan bahwa itu memang disengaja.

## Prinsip terkait

- [Single Responsibility](/id/docs/principles/architecture/single-responsibility) — satukan mengikuti tepat satu alasan untuk berubah.
- [Conway's Law](/id/docs/principles/architecture/conways-law) — batas organisasi menentukan apakah shared code menjadi jembatan atau medan pertempuran.
- [You Aren't Gonna Need It](/id/docs/principles/design/yagni) — rule of three adalah YAGNI yang diterapkan pada abstraction.
- [Explicit Contracts](/id/docs/principles/api/explicit-contracts) — shared code membutuhkan contract yang eksplisit dan berversi.
- [Least Astonishment](/id/docs/principles/design/least-astonishment) — sebuah shared abstraction tidak boleh mengejutkan kedua consumer-nya.
