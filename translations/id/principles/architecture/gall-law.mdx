<AIInstruction>
Ship the simplest system that works end-to-end, then grow it under real usage. Never plan a greenfield build as a single big-bang delivery of the final architecture — plan it as a sequence of working systems. When a design cannot be reached incrementally, treat that as a design flaw, not a scheduling problem.
</AIInstruction>

<Severity level="important" />

## Definition

Complex systems that work are invariably evolved from simple systems that worked; complex systems designed from scratch cannot be debugged into working, because you cannot debug something that has never run. The design task is therefore not to specify the final system but to specify the next small working system and the growth path between the steps. Ambition is allowed; big-bang delivery of ambition is not.

## When to use

- Greenfield products and platforms where requirements are still hypotheses.
- Migrations and rewrites — plan them as staged, strangler-style steps with running value at each stage.
- Architecture roadmaps: each phase must work, not merely assemble toward the end state.
- Anything where real usage patterns are unknown until users arrive.

## When NOT to use

- Re-implementing a proven, fully specified system — the final design is genuinely known; treat it as engineering, not exploration.
- Contractual or regulated deliverables that fix scope up front; deliver the simple core plus the mandatory control planes, not speculative features.
- Small utilities that are already the simple system — no evolution needed.
- Not an excuse to skip hard-to-reverse thinking: data models, security boundaries, and service seams deserve up-front care even while everything else stays simple.

## Anti-pattern

- A 200-page spec, a one-year build, and a launch date where the system runs for the first time.
- Building "the platform" before the first product that would run on it.
- Abstractions for imagined future scale — multi-region, multi-tenant, plugin systems with no plugins.
- Freezing a failed first version because "we already designed it" instead of evolving it.

## Code example

Wrong — the enterprise scaffold that must be completed before anything works:

```ts
// 14 packages, 0 served requests: EventBus, TenantResolver, RegionRouter...
export class EnterprisePlatform {
  async start() { /* still wiring — no behavior exists to test against */ }
}
```

Right — one vertical slice that works, plus a stated growth path:

```ts
// day 1: a request goes through; the team learns from real traffic
export async function signup(req: Request) {
  const user = await db.users.insert(parseSignup(req));
  await mailer.send(welcome(user));
}
// Growth path: extract the mailer behind a port when a second sender appears;
// shard db.users when measured load demands it — not before.
```

## Technical enforcement

<Enforcement>
This principle is enforced by process gates, not by intent:

- **Milestone gates**: no increment counts as done without a demo running end-to-end in a production-like environment.
- **WIP limits**: cap concurrent unfinished layers — an ever-growing unfinished platform is the signature failure this law warns about.
- **RFC discipline**: every proposal must answer "what is the smallest version that runs?" and "what will we learn from it?".
- **Metrics before scale**: dashboards and load data are prerequisites for approving the next complexity step.
</Enforcement>

## Real-world case

<RealCase>
A company funded a one-year, 200-page-spec "enterprise platform": shared auth, workflow engine, reporting framework, and only then the first business module. Integration testing started at month ten and found the layers did not fit, while requirements had drifted for a year without feedback. The project was cancelled before serving a single customer. A rival internal team shipped a crude single-purpose service in six weeks, learned from real users, and quietly absorbed the business need. </RealCase>

## Tension and trade-off

- **Evolution vs. up-front design**: some decisions (data model, security boundaries, service seams) are expensive to reverse — invest in those early even while everything else stays simple; see Chesterton's Fence for what already exists.
- **Growth path vs. YAGNI**: YAGNI says do not build the future; this law says plan the path to it. The compromise: build only the current working system, but avoid decisions that block the next one.
- **Simple-first vs. safety obligations**: "start simple" never starts unsafe — auth, backups, and least-authority must exist in version one, simple but present.
