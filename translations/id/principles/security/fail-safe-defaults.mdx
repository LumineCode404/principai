## Definisi

Ketika sebuah sistem gagal, tidak yakin, atau sekadar baru dimulai, ia harus jatuh ke keadaan yang menolak akses dan tidak melakukan aksi destruktif. Permission adalah grant yang positif dan eksplisit per aksi — bukan asumsi yang bertahan sampai seseorang ingat untuk mencabutnya. Inilah fail-safe defaults dari Saltzer dan Schroeder: dasarkan keputusan akses pada permission, bukan pada eksklusi, karena keadaan default-nya adalah tidak ada permission sama sekali.

## Kapan pakai

- Operasi destruktif: delete, drop, force-push, purge, teardown, bulk update.
- Access control pada API dan service: authentication dan authorization di setiap jalur.
- Script dan otomasi yang dijalankan manusia lelah, di jendela waktu yang salah, di server yang salah.
- Fitur dan flag baru: rilis dalam keadaan nonaktif, aktifkan secara sengaja, per lingkungan.

## Kapan TIDAK pakai

- Konten publik read-only di mana penolakan justru menggagalkan tujuan produk — grant untuk anonim itu eksplisit dan global, bukan default yang terlupa.
- Endpoint liveness yang harus tetap menjawab selama kegagalan parsial agar orchestrator tidak mematikan semua instance sekaligus — fail-open yang disengaja dan terdokumentasi.
- Lingkungan yang dinyatakan eksplisit sebagai disposable, di mana penolakan tidak melindungi apa pun.

## Anti-pattern

- CLI cleanup di mana eksekusi destruktif adalah default dan flag dry-run harus diingat setiap kali.
- Endpoint admin yang dibiarkan dapat diakses semua user terautentikasi karena role check-nya tidak pernah ditulis.
- Aturan firewall yang ditulis sebagai "izinkan semuanya, lalu tolak port yang buruk".
- Timeout pada auth service yang meloloskan request "agar user tidak terblokir".
- Flag yang makna lamanya sudah terlupa, sehingga kini mengaktifkan code path yang tidak pernah dimaksudkan untuk dijalankan siapa pun.

## Contoh kode

Salah — pengaman bersifat opt-in, destruksi adalah default:

```bash
# Flag pengaman harus diingat pada setiap pemanggilan.
./bin/purge-old-records --older-than 30d
# → terhubung ke prod, menghapus baris, tanpa konfirmasi, tanpa preview
# Pada satu-satunya kali operator sedang lelah, perilaku aman itu tidak terjadi.
```

Benar — destruksi membutuhkan grant eksplisit per eksekusi:

```python
# Menghapus bersifat opt-in; jalur default hanya bisa mencetak.
parser.add_argument("--older-than", required=True, help="age cutoff, e.g. 30d")
parser.add_argument("--apply", action="store_true",
                    help="actually delete; without this flag the script only prints")
args = parser.parse_args()
plan = select_records_older_than(args.older_than)
if not args.apply:
    print_plan(plan)        # fail-safe default: tampilkan, jangan sentuh
    sys.exit(0)
delete(plan)                # grant eksplisit, hanya berlaku untuk eksekusi ini
```

## Penegakan teknis

<Enforcement>
Prinsip ini tidak ditegakkan oleh tekad. Tegakkan dengan kontrol nyata:

- **Middleware deny-first**: kebijakan dasar authorization yang terpasang di setiap route secara konstruksi; route memilih masuk (opt in) ke sebuah permission, tidak pernah keluar dari check.
- **Flag yang lahir nonaktif**: platform feature-flag di mana flag baru default-nya off, dan code path mati membutuhkan pengaktifan eksplisit per lingkungan.
- **Timeout yang fail-closed**: lookup policy dan auth yang timeout harus menolak request; fail-open adalah pengecualian yang eksplisit, ter-review, dan terdokumentasi.
- **Destruksi dua langkah**: operasi yang tak dapat dibatalkan membutuhkan langkah konfirmasi terpisah atau aktor kedua, ditegakkan oleh tooling, bukan oleh ingatan.
- **Yang mencegah vs. yang mendeteksi**: middleware default-deny dan flag yang nonaktif secara default mencegah aksi itu terjadi bahkan ketika handler-nya buggy; audit atas flag dan grant hanya mendeteksi drift setelahnya.
</Enforcement>

## Kasus nyata

<RealCase>
Pada 31 Januari 2017, seorang operator GitLab, kelelahan setelah berjam-jam melawan kegagalan replikasi, menghapus direktori di server yang salah — server yang memuat data live database utama. Perintah destruktif itu tersedia secara default di konteks kerjanya: tidak ada yang memaksa dry-run, konfirmasi, atau check kedua sebelum delete yang tak dapat dibatalkan. Sekitar 300 GB data hilang, dan sekitar enam jam penulisan database terbukti tak dapat dipulihkan karena restore yang tersedia lebih lambat dan kurang lengkap dari yang diperkirakan. Fail-safe defaults tidak akan menghentikan kesalahan awal itu, tetapi akan mengurangi satu perintah satu baris menjadi rencana tercetak dan sesaat rasa malu. Postmortem: https://about.gitlab.com/blog/2017/02/01/gitlab-dotcom-database-incident/
</RealCase>

## Tensi dan trade-off

- **Fail-closed vs. graceful degradation**: ketika sebuah dependency gagal, menolak segalanya mengubah outage-nya menjadi outage kita — putuskan per jalur, sebelum insiden terjadi, apakah fail-closed itu proporsional.
- **Deny by default vs. least astonishment**: operator yang berulang kali menabrak penolakan tak terduga belajar memasang flag force secara refleks; grant harus mudah diberikan, terlihat saat diberikan, dan mudah dinalar.
- **Grant eksplisit vs. least authority**: grant per aksi di mana-mana berubah menjadi seremoni; persempit grant-nya sendiri sehingga memperbaruinya terasa aman, bukan menyebalkan.

## Prinsip terkait

- [Least Authority](/id/docs/principles/security/least-authority) — aturan kembar: grant itu sempit, dan keraguan berarti penolakan.
- [Secure by Default](/id/docs/principles/security/secure-by-default) — gagasan yang sama diterapkan pada konfigurasi yang dikirim.
- [Defense in Depth](/id/docs/principles/security/defense-in-depth) — default-deny adalah satu lapisan, bukan seluruh tembok.
- [Blast Radius](/id/docs/principles/reliability/blast-radius) — penahanan untuk hari ketika sebuah penolakan gagal atau dilewati.
- [Least Astonishment](/id/docs/principles/design/least-astonishment) — default yang aman namun tetap masuk akal bagi orang yang menabraknya.
