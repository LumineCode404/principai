<AIInstruction>
Ubah contract yang sudah dipublikasikan hanya melalui versi baru, dan jaga versi lama tetap bekerja selama deprecation window yang diumumkan. Jangan pernah mengubah makna sebuah versi yang sudah ada — bukan type sebuah field, bukan kode error, bukan default. Sebelum menghapus apa pun, ukur siapa yang masih memakainya, dan lakukan sunset berdasarkan bukti, bukan harapan.
</AIInstruction>

<Severity level="important" />

## Definisi

Setelah sebuah contract menjadi publik, maknanya membeku: perubahan dikirim sebagai versi baru (major semver untuk library, versi API untuk service, langkah expand-contract untuk database), sementara versi lama di-deprecate, dipantau, dan akhirnya dihapus menurut jadwal yang dipublikasikan. Mengubah semantik secara diam-diam di bawah nomor versi yang sama adalah dosa besar — itu merusak consumer yang sudah melakukan semuanya dengan benar. Versioning adalah cara mempertahankan kebebasan berubah tanpa mengklaim hak untuk mengejutkan.

## Kapan pakai

- Permukaan API publik dan shared library dengan consumer yang berada di luar kendali.
- API internal lintas tim tempat consumer deploy secara independen.
- Perubahan schema database yang dibaca service lain — berpasangan dengan expand-contract.
- Setiap removal, rename, perubahan type, atau perubahan perilaku atas sesuatu yang sudah terkirim.

## Kapan TIDAK pakai

- Eksperimen pra-1.0 tempat consumer dengan sadar menerima churn — itu konvensi 0.x milik semver sendiri.
- Tooling internal ber-consumer tunggal yang dideploy serentak dengan pemanggilnya.
- Darurat keamanan: tetap berversi, tetapi window-nya menyusut menjadi "umumkan dengan lantang, perbaiki sekarang" — timbangkan bahayanya terhadap kerusakan, alih-alih menunggu kalender berjalan.

## Anti-pattern

- Sebuah field response diam-diam berganti type dari string ke number di dalam versi yang sama.
- Sebuah rilis "minor" mengganti nama kolom atau memperketat validasi yang dulu lolos.
- Deprecation lewat exception — sekarang melempar error, jadi pemanggil "tahu".
- Menghapus sebuah field atau package karena "seharusnya tidak ada yang memakai" — Hyrum's Law menjamin ada seseorang.
- Mendeprecate tanpa metrik usage: tanggal sunset adalah tebakan, dan tebakan itu adalah outage milik seseorang.

## Contoh kode

Salah — versi sama, makna baru:

```ts
// GET /v1/plans — price dulu "19.99" (string desimal); kini 1999 (cents)
app.get('/v1/plans', (req, res) => {
  res.json(plans.map(p => ({ ...p, price: p.priceCents }))); // pembalikan type yang diam-diam
});
```

Benar — perubahan additive, makna lama dibawa melalui deprecation window:

```ts
app.get('/v1/plans', (req, res) => {
  res.json(plans.map(p => ({
    ...p,
    price: (p.priceCents / 100).toFixed(2), // makna v1 dipertahankan — tidak berubah
    price_cents: p.priceCents,              // additive; field lama diberi deprecation header
  })));
});
```

## Penegakan teknis

<Enforcement>
Prinsip ini ditegakkan oleh CI gate dan counter, bukan oleh release notes:

- **Semver linter dan API diff gate**: semantic-release atau tool API diff menggagalkan build ketika perubahan shape yang breaking dikirim tanpa kenaikan versi.
- **OpenAPI diff di CI**: delta contract setiap PR diklasifikasikan (breaking / additive / compatible), dan perubahan breaking menuntut penanda versi baru.
- **Header dan metrik deprecation**: umumkan lewat response header, lacak usage per field dan per endpoint, dan gerbangkan removal pada hitungan consumer terukur yang mencapai nol.
- **Consumer-driven contract tests** (Pact): consumer lama tetap lolos sampai sunset benar-benar dieksekusi.
- **Database**: migration expand-contract — tambahkan yang baru, dual-write, migrasikan reader, dan baru kemudian hapus yang lama.
</Enforcement>

## Kasus nyata

<RealCase>
Sebuah tim API mengubah type satu field response dari string desimal menjadi number — sebuah "pembersihan", tanpa versi, dalam rilis rutin. Karena JSON dengan senang hati membawa keduanya, tidak ada yang gagal dengan lantang: integrator dengan parser ketat putus di runtime mereka sendiri, sementara yang lain salah membulatkan harga secara diam-diam. Seorang pelanggan menemukannya dalam reconciliation penagihan berminggu-minggu kemudian, dan incident review tak punya metrik deprecation bahkan hanya untuk mengukur siapa yang terdampak. Kenaikan versi dengan window akan mengurangi, bukan mencegah, kerusakan itu — integrator tetap harus mengubah kode, tetapi menurut jadwal yang mereka pilih sendiri. Sepupu dari penghapusan-tanpa-peringatan ini adalah left-pad 2016: sebuah package lenyap tanpa versi, tanpa window, dan ribuan build putus — https://www.theregister.com/2016/03/23/npm_left_pad_chaos/ (verified URL). (ilustratif untuk skenario type-flip; verification: perlu)
</RealCase>

## Tensi dan trade-off

- **Kompatibilitas vs. velocity**: memberi versi pada setiap perubahan adalah seremoni; komprominya adalah additive-by-default — penambahan yang backward-compatible tak butuh major baru, hanya perubahan makna yang butuh.
- **Berversi vs. perilaku yang bocor**: Hyrum's Law menjamin bahwa bahkan permukaan yang berversi membocorkan detail observable (timing, urutan pagination); beri versi pada yang bisa, pantau yang tidak bisa.
- **Window vs. urgensi**: deprecation window yang panjang melindungi consumer yang lambat tetapi menggandakan permukaan yang harus dipelihara; ukurlah window berdasarkan metrik usage, bukan kesantunan.

## Prinsip terkait

- [Hyrum's Law](/id/docs/principles/api/hyrum-law) — mengapa perilaku versi lama tetap diandalkan bahkan di tempat yang tak terdokumentasi.
- [Explicit Contracts](/id/docs/principles/api/explicit-contracts) — Anda tak bisa memberi versi pada apa yang tak pernah dideklarasikan.
- [Expand-Contract](/id/docs/principles/data/expand-contract) — versi prinsip ini untuk schema database.
- [Soft-Delete](/id/docs/principles/data/soft-delete) — deprecation adalah soft-delete untuk contract: hapus hanya dengan bukti.
- [Robustness Principle](/id/docs/principles/api/postel-robustness) — memensiunkan deviasi yang ditoleransi pun harus melewati versi.
- [Supply-Chain Vetting](/id/docs/principles/security/supply-chain-vetting) — pin dan review apa yang Anda andalkan, sebelum perubahan versi orang lain menjadi outage Anda.
