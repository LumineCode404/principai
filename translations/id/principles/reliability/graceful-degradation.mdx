<AIInstruction>
Klasifikasikan setiap dependency sebagai esensial atau opsional sebelum sebuah outage mengklasifikasikannya dengan caranya sendiri. Beri setiap outbound call sebuah timeout, bungkus dengan circuit breaker, dan rancang fallback konkret untuk setiap fitur opsional. Saat overload, buang pekerjaan opsional lebih dulu — jangan pernah biarkan dependency yang lambat menduduki worker thread.
</AIInstruction>

<Severity level="important" />

## Definisi

Sebuah sistem mengalami degradation secara graceful ketika kegagalan atau overload pada satu komponen mengurangi kapabilitas alih-alih ketersediaan: checkout tetap berfungsi sementara carousel rekomendasi lenyap. Ini menuntut klasifikasi dependency menjadi esensial atau opsional sebelum incident, dan pencatatan fallback untuk setiap yang opsional. Partial failure adalah kondisi mapan sistem terdistribusi; pilihan sebenarnya adalah antara layanan parsial yang direncanakan dan outage total yang tak direncanakan.

## Kapan pakai

- Halaman dan API yang menghadap user, dirakit dari banyak service: kembalikan respons esensial, jatuhkan enrichment yang lambat.
- Request path ber-fanout tinggi tempat satu dependency yang lambat bisa membuat seluruh worker pool kelaparan.
- Lonjakan trafik dan brownout pada dependency: lakukan load shedding secara eksplisit sebelum prosesnya mati.
- Sistem ML: sajikan model terakhir yang baik ketika training baru atau feature pipeline tertinggal.

## Kapan TIDAK pakai

- Path kebenaran dan keselamatan — auth, pembayaran, security check — tempat "degraded" berarti fail-open; itu fail-unsafe, bukan graceful (lihat Fail-Safe Defaults).
- Produk yang path esensialnya JUSTRU komponen opsional tersebut (layanan penerjemahan tanpa penerjemahan adalah outage, bukan degradation).
- Path tulis tempat degraded berarti diam-diam menyimpan data yang tidak lengkap — itu menukar outage dengan korupsi (lihat Fail-Visible).

## Anti-pattern

- Render halaman terblokir oleh widget rekomendasi; satu service recs yang lambat mengubah setiap halaman menjadi error.
- Outbound call tanpa timeout; dependency yang lambat perlahan-lahan memiliki setiap worker thread.
- Agregasi all-or-nothing: seluruh bagian respons harus terakit, atau tidak ada apa pun yang dikembalikan.
- Me-retry lebih keras ke dependency yang gagal, alih-alih melepaskannya (lihat Retry Budget).
- Menyajikan konten degraded tanpa sinyal apa pun ke user atau dashboard — tidak ada yang bisa membedakan sehat dari degraded.

## Contoh kode

Salah — satu widget opsional menahan seluruh halaman:

```python
def render_page(user):
    recs = recs_client.get(user.id)      # tanpa timeout, tanpa fallback, path esensial terblokir
    cart = cart_client.get(user.id)
    return template(recs=recs, cart=cart)
```

Benar — buang yang opsional, pertahankan yang esensial:

```python
def render_page(user):
    cart = cart_client.get(user.id, timeout=0.1)          # esensial: timeout keras
    try:
        recs = recs_client.get(user.id, timeout=0.05)     # opsional: budget pendek
    except (Timeout, Unavailable):
        recs = Recommendations.empty()                   # fallback, bukan 500
    return template(recs=recs, cart=cart)
```

## Penegakan teknis

<Enforcement>
Degradation adalah perilaku yang sengaja dirancang, sehingga bisa ditegakkan seperti perilaku rancangan lainnya:

- **Timeout pada setiap outbound call**, diukur terhadap latency SLO dependency — ditegakkan oleh default HTTP client dan service mesh, bukan oleh disiplin per developer.
- **Circuit breaker dengan fallback bernama** yang dipasang di level framework; dependency tanpa fallback tidak boleh dideklarasikan opsional.
- **Admission control sebelum resource habis**: limit queue dan respons busy yang eksplisit disertai panduan retry; OOM killer milik kernel bukanlah strategi load shedding.
- **Degradation harus observable**: metric "served degraded" dan sinyal yang terlihat user (empty state, penanda stale) adalah bagian dari fitur, bukan tambahan opsional.
- **Game day**: matikan satu dependency di staging sesuai jadwal; path inti yang tetap hidup adalah kriteria lulus.
</Enforcement>

## Kasus nyata

<RealCase>
Pada 2019-11-02, Cloudflare men-deploy aturan WAF baru yang berisi regular expression dengan backtracking katastrofik pada input tertentu. Karena bug pada software yang men-deploy aturan, aturan itu live serentak di mesin-mesin edge seluruh dunia alih-alih bertahap; regex itu menghabiskan CPU di mesin-mesin tersebut, dan request di seluruh dunia mengembalikan 502 sampai para engineer memakai kill switch global untuk menonaktifkan WAF sepenuhnya. Postmortem: https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-november-2-2019/ — lapisan security inline ikut menjatuhkan path esensial bersamanya; request di-drop, bukannya disajikan secara degraded. Postmortem yang sama juga merupakan pelajaran tentang Blast Radius dan staged rollout: deployment bertahap yang memang direncanakan akan membatasi efek aturan itu pada subset yang bisa diuji.
</RealCase>

## Tensi dan trade-off

- **Graceful Degradation vs. Fail-Visible**: shedding bisa menutupi error yang sesungguhnya; setiap degradation harus terlihat di metric dan di respons, atau outage hanya tertukar dengan pembusukan yang lambat dan senyap.
- **Graceful Degradation vs. Fail-Safe Defaults**: jangan pernah mendegradasi security check atau safety check demi menjaga response time — security yang degraded adalah pelanggaran (breach), bukan outage.
- **Ditimbang terhadap Least Astonishment**: sampaikan kepada user apa yang hilang atau stale; halaman yang diam-diam berbohong tentang kebaruan datanya mengikis kepercayaan lebih dalam daripada state degraded yang jujur.

## Prinsip terkait

- [Retry Budget](/id/docs/principles/reliability/retry-budget) — berhenti memberi makan dependency yang gagal; lepaskan saja.
- [Observability First](/id/docs/principles/reliability/observability-first) — degradation yang tak terlihat tidak bisa dibedakan dari kegagalan.
- [Fail-Visible](/id/docs/principles/reliability/fail-visible) — gagal dengan keras di layer yang memiliki keputusan, degrade di layer yang memiliki user.
- [Fail-Safe Defaults](/id/docs/principles/security/fail-safe-defaults) — tolak secara default; check esensial tidak pernah "mendegradasi" diri menjadi mengizinkan.
