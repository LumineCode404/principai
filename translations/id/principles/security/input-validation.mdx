<AIInstruction>
Validasi setiap input di trust boundary — body request, header, query string, isi file, pesan queue, input model — sebelum ia mencapai storage, command, atau business logic. Jangan pernah percaya bahwa caller, service partner, atau frontend kita sendiri sudah memvalidasi. Jika kita tidak bisa menyatakan dengan tepat seperti apa bentuk data yang valid, berhenti dan tanyakan kepada manusia sebelum menulis handler-nya.
</AIInstruction>

<Severity level="critical" />

## Definisi

Setiap tempat data menyeberang dari konteks yang kurang dipercaya ke konteks yang lebih dipercaya adalah trust boundary, dan semua yang menyeberang harus diperiksa type, shape, size, range, dan encoding-nya sebelum menyentuh state. Validasi adalah penjaga pintu, bukan tim pembersih: input yang malformed ditolak di pintu, bukan diperbaiki di downstream tempat maknanya tidak diketahui. Hal yang sama berlaku untuk panjang dan batas — check itu milik boundary, bukan "akhirnya".

## Kapan pakai

- Endpoint API dan webhook — boundary yang paling kanonik.
- Layer database yang menerima tulisan dari lebih dari satu producer.
- Consumer queue dan stream: pesan sering hidup lebih lama daripada kode yang memproduksinya.
- Import, upload, dan pipeline ML: data training, file, feed pihak ketiga.
- Apa pun yang dirangkai menjadi shell command, query, atau file path.

## Kapan TIDAK pakai

- Di dalam satu modul yang inputnya sudah divalidasi di boundary publiknya — memvalidasi ulang setiap panggilan internal hanyalah derau.
- Pipeline telemetry dan logging yang tidak boleh crash: tangkap yang bisa di-parse, hitung sisanya sebagai dropped.
- Store yang kontraknya menyimpan byte secara buram — validasi menjadi milik siapa pun yang menafsirkan blob itu nanti.

## Anti-pattern

- Memvalidasi hanya field yang dikirim UI saat ini; field baru datang tanpa check.
- Sanitasi lewat penggantian string — buang kutip, escape tanda minus — alih-alih mem-parse menjadi struktur yang sudah diketahui baik.
- Memercayai service internal "karena itu milik kita"; boundary-nya tetap ada.
- Menegakkan panjang field di frontend dan berasumsi hanya frontend yang memanggil API.
- Memperbaiki input malformed secara diam-diam: memaksa konversi, memangkas, menebak — lalu lanjut dengan nilai yang tidak pernah dikirim siapa pun.

## Contoh kode

Salah — merangkai query dari string input yang belum divalidasi:

```python
# Tidak ada check boundary: type, shape, dan length semuanya asumsi
def find_orders(request):
    user_id = request.args.get("user_id")
    status = request.args.get("status", "open")
    sql = f"SELECT * FROM orders WHERE user_id = {user_id} AND status = '{status}'"
    return db.execute(sql)     # satu user_id yang diracik membaca seluruh tabel
```

Benar — parse, validasi, tolak di boundary:

```python
def find_orders(request):
    try:
        user_id = parse_uuid(request.args["user_id"])       # type yang pasti
        status = request.args.get("status", "open")
        if status not in {"open", "paid", "shipped"}:       # allowlist tertutup
            raise ValueError("bad status")
    except (KeyError, ValueError) as e:
        return reject(400, str(e))     # ditolak di pintu, state tak tersentuh
    return db.query(Order).filter_by(user_id=user_id, status=status).all()
```

## Penegakan teknis

<Enforcement>
Validasi harus struktural, bukan aspiratif:

- **API schema-first**: schema request bertipe yang menolak field tak dikenal atau malformed sebelum kode handler berjalan — validasi sebagai perpipaan, bukan kedisiplinan.
- **Hanya jalur akses berparameter**: query berparameter, prepared statement, helper path-join yang aman; CI melarang SQL dan shell command yang dirangkai dari string.
- **Batas di gateway**: batas ukuran request, batas panjang field, dan timeout sebelum parsing yang mahal dimulai.
- **Fuzzing di CI**: input malformed di-generate terhadap setiap endpoint; crash dan leak menggagalkan build.
- **Yang mencegah vs. yang mendeteksi**: schema dan parameterisasi mencegah data malformed mencapai logic; fuzzing dan log mendeteksi celah setelah percobaan terjadi — jalankan keduanya, jangan pernah berasumsi yang pertama sudah lengkap.
</Enforcement>

## Kasus nyata

<RealCase>
Heartbleed (CVE-2014-0160), diungkap pada April 2014, adalah hilangnya bounds check tepat di trust boundary: ekstensi heartbeat TLS di OpenSSL mengambil panjang payload yang diklaim oleh peer lalu memantulkan kembali byte sebanyak itu tanpa memverifikasi bahwa buffer benar-benar memuatnya. Pesan yang diracik dengan klaim payload besar membuat penyerang dapat membaca memori server — session token, password, dan pada kasus terburuk private key — tanpa jejak di log. Input itu dipercaya tepat di tempat ia seharusnya diukur. Validasi boundary yang ketat tidak akan mencegah setiap bug OpenSSL di masa depan, tetapi akan mengurangi bug yang satu ini dari "membaca memori proses secara remote" menjadi "menolak heartbeat yang malformed". Detail: https://heartbleed.com/
</RealCase>

## Tensi dan trade-off

- **Validasi vs. robustness Postel**: sikap longgar dalam menerima mendatangkan interoperabilitas dan menyembunyikan bug caller; di security boundary, keketatan yang menang — bersikap longgar hanya di tempat kita sanggup menanggung tebakannya.
- **Memperketat validasi vs. versioned contracts**: aturan yang lebih ketat menolak client yang dulu diizinkan contract lama — perketat lewat versi baru, bukan dengan menyergap client yang sudah ada.
- **Penolakan dini vs. graceful degradation**: menolak input malformed dengan cepat melindungi state, tetapi banjir traffic buruk bisa menjadi badai yang terlihat oleh user — pasangkan penolakan dengan rate limiting dan error yang jelas.

## Prinsip terkait

- [Fail-Safe Defaults](/docs/principles/security/fail-safe-defaults) — apa yang terjadi pada input yang tidak kita rencanakan.
- [Defense in Depth](/docs/principles/security/defense-in-depth) — validasi adalah tembok terluar, bukan satu-satunya.
- [Complete Mediation](/docs/principles/security/complete-mediation) — kembaran access-control: validasi datanya, mediasi otoritasnya, setiap kali.
- [Postel's Robustness](/docs/principles/api/postel-robustness) — tensinya, dinyatakan secara jujur.
- [Versioned Contracts](/docs/principles/api/versioned-contracts) — cara memperketat validasi tanpa menyergap client.
- [Explicit Contracts](/docs/principles/api/explicit-contracts) — aturan validasi milik contract, bukan pengetahuan yang hanya hidup di kepala tim.
