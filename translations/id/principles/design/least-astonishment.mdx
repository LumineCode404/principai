<AIInstruction>
Jadikan tafsir yang paling jelas sebagai tafsir yang benar: nama, default, dan bentuk API harus mengikuti konvensi dominan platform. Nyatakan setiap side effect sebuah operasi di namanya, di dokumentasinya, atau di responsnya. Sebelum mengirim sebuah perilaku, tanyakan apakah seorang pembaca bisa memprediksinya hanya dari signature-nya. Jika hal itu akan mengejutkan Anda sebagai caller, ubah — atau dokumentasikan dengan sangat mencolok.
</AIInstruction>

<Severity level="advisory" />

## Definisi

Sebuah komponen dirancang dengan baik ketika perilakunya cocok dengan apa yang diprediksi pembaca yang cakap dari namanya, signature-nya, dan konvensi di sekitarnya. Kejutan adalah bug desain bahkan ketika perilakunya benar secara teknis — pembaca bertindak berdasarkan asumsi kelirunya, dan kerusakan mendarat di data. Konvensi mengerjakan sebagian besar pekerjaan: mengikuti default platform biasanya lebih penting daripada kepintaran lokal.

## Kapan pakai

- Menamai apa pun yang publik: endpoint, fungsi, flag, config key.
- Memilih default — default seharusnya adalah kasus yang paling aman dan paling umum, bukan yang paling fleksibel.
- Desain surface API dan library, termasuk respons error dan respons kosong.
- Alur UX dan interaksi CLI tempat muscle memory membawa pengguna.

## Kapan TIDAK pakai

- Ketika konvensinya sendiri berbahaya — mengejutkan-tapi-aman mengalahkan akrab-tapi-destruktif (lihat Secure by Default).
- Surface legacy dengan banyak caller yang sudah ada — mengubah perilaku mengejutkan-yang-sudah-terkirim memecahkan dunia (lihat Hyrum's Law); versikan perubahannya.
- Domain tanpa konvensi yang mapan — pilihan Anda menjadi konvensinya; buat sekali, secara terpusat, dan dokumentasikan secara mencolok.

## Anti-pattern

- Endpoint delete yang juga menghapus record dependen tanpa mengatakannya.
- Getter yang menulis; method list yang mem-paginate berbeda dari setiap list lain di codebase.
- Flag yang namanya menjanjikan lebih sedikit dari kelakuannya — purgeCache yang juga memutus koneksi.
- Error yang ditelan dan diganti respons sukses kosong.
- Default yang timezone-naive atau locale-naive dalam produk global.

## Contoh kode

Salah — magic yang "membantu":

```ts
// DELETE /users/:id — juga diam-diam menghapus invoice dan token user itu
async function deleteUser(id: string) {
  await db.users.delete(id);
  await db.invoices.deleteMany({ userId: id }); // kejutan: cascade yang tak terdokumentasi
  await db.tokens.deleteMany({ userId: id });   // kejutan: session mati secara senyap
}
```

Benar — tafsir yang paling jelas adalah tafsir yang benar:

```ts
// Menghapus user menghapus user. Tidak lebih.
async function deleteUser(id: string) {
  await db.users.delete(id);
}

// Purge data adalah operasi terpisah, bernama, dan eksplisit
async function purgeUserData(id: string) {
  await db.users.delete(id);
  const invoices = await db.invoices.deleteMany({ userId: id });
  return { deletedInvoices: invoices.count }; // responsnya mengakui apa yang telah terjadi
}
```

## Penegakan teknis

<Enforcement>
Kejutan bisa diuji jika Anda menjadikannya demikian:

- **Contract test**: test otomatis menegaskan bahwa setiap endpoint hanya melakukan efek yang terdokumentasi; cascade yang tak terdokumentasi menggagalkan CI.
- **Checklist review API**: "daftar semua efek operasi ini — apakah masing-masing ada di nama, di docs, atau di respons?" Efek yang tak terdaftar tidak ikut terkirim.
- **Penegakan schema**: schema OpenAPI (atau setaranya) divalidasi terhadap respons aktual di CI, sehingga kejutan muncul ke permukaan sebelum menimpa consumer.
- **Linting konvensi**: aturan penamaan untuk flag, config key, dan endpoint; penyimpangan dari pattern mapan proyek mengharuskan ADR.
</Enforcement>

## Kasus nyata

<RealCase>
Sebuah platform internal menyediakan endpoint delete untuk record user. Untuk "menghemat caller satu round trip", endpoint itu juga menghapus record dependen milik user — invoice, API key, audit entry — tanpa mendokumentasikan atau melaporkan cascade-nya. Para caller, terpola pada setiap endpoint delete lain di perusahaan (yang mengembalikan conflict ketika ada dependensi), mengasumsikan penghapusan satu baris. Sebuah skrip offboarding rutin menghapus ratusan record dependen dalam satu sore; karena cascade-nya senyap, kehilangan itu baru ditemukan berhari-hari kemudian oleh rekonsiliasi, bukan oleh operatornya. Perbaikannya bukan sekadar dokumentasi: cascade itu menjadi endpoint purge yang terpisah dan eksplisit, yang responsnya melaporkan semua yang ia hapus — mengurangi, bukan mencegah, kerusakan dari asumsi keliru berikutnya. </RealCase>

## Tensi dan trade-off

- **Least Astonishment vs Postel's Robustness**: menerima dan memperbaiki input yang malformed secara diam-diam juga sebuah kejutan — caller tak pernah tahu bahwa request-nya salah. Utamakan explicit contract dengan error yang nyaring dan actionable daripada pemaafan yang senyap.
- **Least Astonishment vs Hyrum's Law**: apa pun yang Anda kirim menjadi load-bearing; perilaku mengejutkan yang sudah terkirim tidak bisa begitu saja diperbaiki tanpa memecahkan para dependent-nya. Versikan koreksinya (lihat Versioned Contracts).
- **Kenyamanan vs prediktabilitas**: convention-over-configuration dan smart default menghemat waktu orang dalam dan mengejutkan pendatang baru. Anggarkan magic-nya, dan buat default yang tersembunyi mudah ditemukan.

## Prinsip terkait

- [Postel's Robustness](/id/docs/principles/api/postel-robustness) — pemberat yang abadi: kemurahan dalam apa yang diterima.
- [Hyrum's Law](/id/docs/principles/api/hyrum-law) — perilaku yang terkirim, diinginkan atau tidak, menjadi contract.
- [Explicit Contracts](/id/docs/principles/api/explicit-contracts) — efek yang didokumentasikan dan ditegakkan adalah efek yang tidak bisa mengejutkan.
- [Soft Delete](/id/docs/principles/data/soft-delete) — penghapusan yang reversibel menekan biaya dari satu asumsi keliru.
- [Fail Visible](/id/docs/principles/reliability/fail-visible) — ketika kejutan tetap terjadi, ia harus terlihat.
