<AIInstruction>
Buat setiap kegagalan terdengar keras, seketika, dan jelas asalnya: raise error-nya, keluar dengan exit code nonzero, buat build-nya gagal. Jangan pernah menelan exception, jangan pernah mengembalikan nilai default setelah operasi gagal, jangan pernah lanjut melewati precondition yang gagal. Hasil parsial yang senyap lebih buruk daripada crash — jika sebuah kegagalan tidak bisa digolongkan sebagai tidak berbahaya, sampaikan kepada manusia.
</AIInstruction>

<Severity level="important" />

## Definisi

Fail-visible berarti error mengumumkan dirinya sendiri di titik kegagalannya — sebuah exception, exit nonzero, build merah — alih-alih menyebarkan data yang salah ke hilir. Alternatifnya, kegagalan senyap, mengubah perbaikan lima menit menjadi berminggu-minggu state terkorupsi: sistem terus "bekerja" sambil berbohong secara diam-diam. Fail-fast adalah separuh aturan yang operasional: semakin cepat sebuah defect menghentikan eksekusi, semakin dekat henti itu dengan defect yang menyebabkannya.

## Kapan pakai

- Pipeline data: record yang buruk harus dibelokkan dengan keras, bukan menolkan satu field lalu lanjut.
- CI/CD dan skrip: exit nonzero dan build merah; check yang berubah hijau sambil tak melakukan apa-apa sedang berbohong.
- Desain library: input tidak valid atau state mustahil harus raise, jangan pernah menebak maksudnya.
- Panggilan terdistribusi: timeout dan error dikembalikan ke pemanggil, jangan pernah diserap menjadi default.

## Kapan TIDAK pakai

- Manisnya UI yang best-effort (avatar yang gagal menampilkan placeholder) — itu graceful degradation, dan bedanya ada di niat: fallback yang sengaja didesain dan terlihat, bukan telan yang tidak sengaja.
- Error transient di dalam retry loop yang diawasi — asalkan supervisor membunyikan alarm begitu budget-nya habis (lihat Retry Budget).
- Jalur verifikasi yang kritis bagi keamanan, di mana "gagal" juga harus berarti "fail closed" — terlihat tapi terbuka adalah pelanggaran (lihat Fail-Safe Defaults).

## Anti-pattern

- Klausa except yang menelan segalanya dan mengembalikan None — pemanggil tak bisa membedakan "tidak ada data" dari "tidak bisa memeriksa".
- Check CI yang exit nol saat tooling-nya sendiri hilang, "agar build tetap hijau".
- Error ditulis ke log yang tak dibaca siapa pun sementara API mengembalikan sukses.
- Jatuh ke config default saat parsing config gagal — service berjalan dengan setting yang tak diketahui.
- Fungsi verifikasi yang mengembalikan sukses padahal langkah internalnya tidak berjalan.

## Contoh kode

Salah — validasi dilewati secara diam-diam:

```python
def find_user_or_none(payload):
    try:
        return store.find_user(payload["user_id"])
    except Exception:
        return None            # pemanggil melihat "tidak ada user"; store yang down tak terlihat
```

Benar — keras, seketika, jelas asalnya:

```python
def find_user(payload):
    try:
        return store.find_user(payload["user_id"])
    except KeyError as e:
        raise InvalidPayload(f"missing field {e}")          # error input, dinamai
    except StoreUnavailable as e:
        raise LookupFailed("user store unreachable") from e  # error infra, berantai, terlihat
```

## Penegakan teknis

<Enforcement>
Keheningan adalah masalah lint dan desain — tegakkan secara mekanis:

- **Aturan lint**: catch block kosong dan penelanan exception menyeluruh memfailkan CI di rule set default sebagian besar linter; aktifkan.
- **Disiplin skrip**: template bash proyek hadir dengan strict error mode (exit saat error, gagal saat variabel unset, gagal saat pipe failure); setiap skrip mewarisinya.
- **Dead-man switch**: proses yang harus terus berjalan menerbitkan heartbeat; hilangnya heartbeat itulah alarmnya — zombie senyap tak bisa bersembunyi.
- **Checklist review**: setiap cabang except/catch baru harus menyebutkan apa yang dilakukannya terhadap error itu.
- **Visibilitas agregat**: jumlah dari kegagalan-kegagalan keras yang individual tetap terlihat sebagai error ratio di sebuah dashboard (lihat Observability First).
</Enforcement>

## Kasus nyata

<RealCase>
Pada Februari 2014, Apple memperbaiki bug verifikasi TLS yang telah ikut terkirim dalam kode SSL/TLS-nya selama beberapa waktu: baris "goto fail;" yang terduplikasi, tereksekusi tanpa syarat karena pernyataan if di sekitarnya tidak memakai kurung kurawal, melompat ke label penanganan error dengan nilai error nol (sukses). Pemeriksaan signature sisanya dilewati, dan sistem yang terdampak bisa menerima koneksi terlepas dari signature servernya. Tidak ada yang error, tidak ada yang tercatat — mode kegagalannya adalah "sukses", dan bug itu hanya bisa ditemukan dengan membaca kode, bukan dengan mengawasi production. Writeup: https://www.imperialviolet.org/2014/02/22/applebug.html — satu kegagalan yang terlihat pada cabang itu akan mengurangi bypass keamanan yang senyap menjadi laporan bug biasa.
</RealCase>

## Tensi dan trade-off

- **Fail-Visible vs. resiliensi**: menelan-lalu-lanjut menjaga demo tetap hidup tapi meracuni data; timbang menurut apakah data yang salah bisa dipulihkan nanti — biasanya tidak.
- **Fail-Visible vs. Graceful Degradation**: gagalkan dengan keras di layer yang memiliki keputusan, lakukan degradasi secara terlihat di layer yang memiliki pengalaman pengguna; error yang sama adalah crash di sebuah library dan banner ramah di UI.
- **Ditimbang terhadap Least Astonishment**: keras berarti jelas dan jelas asalnya, bukan berisik — dinding stack trace yang identik menyembunyikan satu sinyal nyata seefektif keheningan.

## Prinsip terkait

- [Observability First](/id/docs/principles/reliability/observability-first) — error yang di-raise membutuhkan metrik dan trace yang menunggunya.
- [Graceful Degradation](/id/docs/principles/reliability/graceful-degradation) — fallback yang disengaja dan terlihat di layer UX.
- [Fail-Safe Defaults](/id/docs/principles/security/fail-safe-defaults) — di jalur verifikasi, gagal secara terlihat juga harus berarti fail closed.
- [Retry Budget](/id/docs/principles/reliability/retry-budget) — hanya error transient dan terlihat yang layak masuk retry loop.
