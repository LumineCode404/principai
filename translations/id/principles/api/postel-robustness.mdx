Buat output sesuai persis dengan contract yang dipublikasikan — ketat di sisi pengiriman. Di sisi penerima, terima hanya deviasi yang sudah dituliskan, dan tolak sisanya dengan error yang jelas. ## Definisi

Robustness Principle (RFC 1122, section 1.2.2) punya dua separuh: implementasi yang mengirim harus konservatif — konforman secara ketat — sementara implementasi yang menerima boleh liberal, menoleransi input yang tidak sempurna tetapi masih bisa ditafsirkan. Disiplin modern menambahkan klausul ketiga: liberalitas harus berbatas, terdokumentasi, dan observable. Toleransi yang tidak dituliskan maupun di-log bukanlah robustness; ia adalah kecelakaan yang menunggu menjadi dependency milik orang lain.

## Kapan pakai

- API publik dan endpoint protokol yang melayani banyak client heterogen atau legacy.
- Parser untuk format di luar kendali sendiri: email, feed, ekspor CSV, webhook pihak ketiga.
- Layer gateway atau proxy yang harus menjaga partner yang tidak sempurna tetap berjalan selagi ekosistem membereskan dirinya.

## Kapan TIDAK pakai

- Mem-parse input yang tidak dipercaya tempat data malform adalah attack vector — strictness adalah postur keamanan di sini.
- Internal service mesh yang kedua ujungnya dikuasai sendiri: penolakan ketat menyingkap bug producer pada momen paling awal dan paling murah.
- Di mana pun toleransi akan menyembunyikan kerusakan data alih-alih sekadar merepotkan — nilai yang salah-tetapi-bisa-diparse, diterima "secara liberal", lalu merusak state, lebih buruk daripada request yang ditolak.

## Anti-pattern

- Menerima apa saja dan menebak maksudnya: field yang hilang di-default ke suatu nilai yang masuk akal, tanpa log.
- Koersi diam-diam — string "42" pelan-pelan menjadi angka 42, dan "abc" menjadi 1.
- Bersikap liberal dalam apa yang dikirim karena "pihak lain juga liberal".
- Menoleransi deviasi bertahun-tahun, lalu menghapus toleransi itu tanpa versi dan tanpa window.

## Contoh kode

Salah — terima apa saja, menebak, dan tak memberi tahu siapa pun:

```ts
app.post('/orders', (req, res) => {
  const qty = Number(req.body.qty) || 1;   // "abc" diam-diam menjadi 1
  const note = req.body.note ?? '';        // null, undefined, false — semua dianggap lumrah
  res.json({ ok: true, qty });            // sudah terkirim; tak akan ada yang pernah tahu
});
```

Benar — inti yang ketat, toleransi dikurung pada satu kasus terdokumentasi dan ter-log:

```ts
// Ketat secara default; SATU kelonggaran terdokumentasi (qty dikirim sebagai string numerik)
const OrderIn = z.object({ qty: z.number().int().positive() }).strict();
app.post('/orders', (req, res) => {
  if (typeof req.body?.qty === 'string') {
    metrics.count('tolerated.qty_as_string'); // toleransi menjadi observable
    req.body.qty = Number(req.body.qty);     // satu-satunya kasus terdokumentasi
  }
  const parsed = OrderIn.safeParse(req.body);
  if (!parsed.success) return res.status(400).json(parsed.error.flatten());
  createOrder(parsed.data);                  // ketat di luar kasus terdokumentasi
});
```

## Penegakan teknis

<Enforcement>
Prinsip ini ditegakkan oleh schema dan test, bukan oleh kesantunan:

- **Schema ketat di boundary** (zod, JSON Schema, protobuf): key tak dikenal ditolak, type persis — toleransi adalah daftar pengecualian yang eksplisit dan terenumerasi di schema atau adapter.
- **Output conformance test di CI**: golden test yang menegaskan response cocok persis dengan spec yang dipublikasikan — separuh pengirim-konservatif itu bisa diuji.
- **Tolerance budget**: setiap deviasi yang diterima mendapat satu baris log dan satu hitungan di dashboard; ketika hitungan bertahan di nol selama satu kuartal, toleransi itu menjadi kandidat deprecation di balik kenaikan versi.
- **Fuzzing** parser di CI untuk membuktikan ia menolak, bukan berimprovisasi, atas input yang malform.
</Enforcement>

## Kasus nyata

<RealCase>
Sebuah API menerima string tanggal bergaya ISO dan dengan "santun" memperlakukan timezone yang hilang sebagai UTC — bertahun-tahun, diam-diam. Sebuah partner kemudian mulai mengirim timestamp waktu lokal; record tersimpan mereka bergeser berjam-jam, dan kerusakan itu muncul berbulan-bulan kemudian dalam reconciliation, tanpa jejak kapan dan mengapa penafsiran yang salah terjadi, karena toleransinya tidak pernah di-log. Parser yang ketat akan menyingkap tanggal malform itu pada saat mereka tiba, bukan berbulan-bulan kemudian. (ilustratif — komposit dari mode kegagalan yang umum; verification: perlu)
</RealCase>

## Tensi dan trade-off

- **Kritik modern — toleransi menumpuk**: puluhan tahun penerimaan liberal melatih ekosistem tempat output malform menjadi kebutuhan de facto (lihat Hyrum's Law), itulah sebabnya desain protokol yang ketat berargumen penerima sebaiknya menolak dan memaksa producer memperbaiki bug-nya sendiri. Simpan toleransi untuk partner yang tak bisa diperbaiki dan untuk transisi yang sudah dijadwalkan.
- **Interoperabilitas vs. keamanan**: setiap deviasi yang diterima adalah area permukaan tanpa validasi; untuk input yang tak dipercaya, strictness menang dengan alasan keamanan.
- **Kebaikan vs. observability**: toleransi senyap itu baik hari ini dan tak terpelihara besok — jalan tengahnya adalah toleransi-dan-log, lalu pensiunkan toleransi itu lewat perubahan yang berversi.

## Prinsip terkait

- [Hyrum's Law](/id/docs/principles/api/hyrum-law) — setiap deviasi yang ditoleransi menjadi dependency seseorang.
- [Explicit Contracts](/id/docs/principles/api/explicit-contracts) — toleransi apa pun yang diizinkan seharusnya hidup di contract, bukan di dongeng kode.
- [Input Validation](/id/docs/principles/security/input-validation) — pasangan yang ketat di boundary yang bermusuhan.
- [Versioned Contracts](/id/docs/principles/api/versioned-contracts) — cara memensiunkan sebuah toleransi tanpa menarik karpet dari bawah kaki.
- [Fail-Visible](/id/docs/principles/reliability/fail-visible) — kapan penolakan mengalahkan penebakan.
