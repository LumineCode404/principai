<AIInstruction>
Validate every input at the trust boundary — request bodies, headers, query strings, file contents, queue messages, model inputs — before it reaches storage, commands, or business logic. Never trust a caller, a partner service, or your own frontend to have already validated. If you cannot state precisely what valid looks like, stop and ask a human before writing the handler.
</AIInstruction>

<Severity level="critical" />

## Definition

Every place data crosses from a less-trusted context into a more-trusted one is a trust boundary, and everything crossing it must be checked for type, shape, size, range, and encoding before it touches state. Validation is the doorman, not the cleanup crew: malformed input is rejected at the door, not repaired downstream where its meaning is unknown. The same goes for lengths and bounds — the check belongs at the boundary, not "eventually".

## When to use

- API endpoints and webhooks — the canonical boundary.
- Database layers that accept writes from more than one producer.
- Queue and stream consumers: messages often outlive the code that produced them.
- Imports, uploads, and ML pipelines: training data, files, third-party feeds.
- Anything shell commands, queries, or file paths are built from.

## When NOT to use

- Inside a single module whose inputs were already validated at its public boundary — re-validating every internal call is noise.
- Telemetry and logging pipelines that must never crash: capture what parses, count the rest as dropped.
- Stores whose contract is to hold bytes opaquely — validation belongs to whoever interprets the blob later.

## Anti-pattern

- Validating only the fields the current UI sends; a new field arrives with no check.
- Sanitizing by string replacement — strip quotes, escape dashes — instead of parsing into a known-good structure.
- Trusting an internal service "because it is ours"; the boundary still exists.
- Enforcing lengths in the frontend and assuming only the frontend calls the API.
- Silently repairing malformed input: coercing, trimming, guessing — then continuing with a value nobody sent.

## Code example

Wrong — string-splicing a query from unvalidated input:

```python
# No boundary check: type, shape, and length are all assumptions
def find_orders(request):
    user_id = request.args.get("user_id")
    status = request.args.get("status", "open")
    sql = f"SELECT * FROM orders WHERE user_id = {user_id} AND status = '{status}'"
    return db.execute(sql)     # one crafted user_id reads the whole table
```

Right — parse, validate, reject at the boundary:

```python
def find_orders(request):
    try:
        user_id = parse_uuid(request.args["user_id"])       # exact type
        status = request.args.get("status", "open")
        if status not in {"open", "paid", "shipped"}:       # closed allowlist
            raise ValueError("bad status")
    except (KeyError, ValueError) as e:
        return reject(400, str(e))     # rejected at the door, state untouched
    return db.query(Order).filter_by(user_id=user_id, status=status).all()
```

## Technical enforcement

<Enforcement>
Validation must be structural, not aspirational:

- **Schema-first APIs**: typed request schemas that reject unknown or malformed fields before handler code runs — validation as plumbing, not discipline.
- **Parameterized access paths only**: parameterized queries, prepared statements, safe path-join helpers; CI bans string-built SQL and shell commands.
- **Limits at the gateway**: request size caps, field length caps, and timeouts before expensive parsing begins.
- **Fuzzing in CI**: malformed inputs generated against every endpoint; crashes and leaks fail the build.
- **What prevents vs. detects**: schemas and parameterization prevent malformed data from ever reaching logic; fuzzing and logs detect the gaps after attempts — run both, never assume the first is complete.
</Enforcement>

## Real-world case

<RealCase>
Heartbleed (CVE-2014-0160), disclosed in April 2014, was a missing bounds check exactly at a trust boundary: OpenSSL's TLS heartbeat extension took a claimed payload length from the peer and echoed back that many bytes without verifying the buffer actually held them. A crafted message claiming a large payload let attackers read server memory — session tokens, passwords, and in the worst case private keys — with no trace in the logs. The input was trusted precisely where it should have been measured. Rigorous boundary validation would not have prevented every future OpenSSL bug, but it would have reduced this one from "read arbitrary process memory remotely" to "reject a malformed heartbeat". Details: https://heartbleed.com/
</RealCase>

## Tension and trade-off

- **Validation vs. Postel's robustness**: being liberal in what you accept buys interoperability and hides caller bugs; at a security boundary, strictness wins — be liberal only where you can afford to guess.
- **Tightening validation vs. versioned contracts**: stricter rules reject clients the old contract allowed — tighten through a new version, not by ambushing existing ones.
- **Early rejection vs. graceful degradation**: rejecting malformed input fast protects state, but a flood of bad traffic can become a user-visible storm — pair rejection with rate limiting and clear errors.
