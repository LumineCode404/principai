<AIInstruction>
Before deleting or changing code you did not write, find out why it exists: git history, tests, linked incidents, and the people who were present. Treat unexplained code as load-bearing until proven otherwise. If you cannot establish why a fence was built, do not remove it — escalate to someone who may know. Land removals as small, separately revertable changes with monitoring attached.
</AIInstruction>

<Severity level="advisory" />

## Definition

Chesterton's fence: a reformer sees a fence across a field and demands its removal; the owner refuses until the reformer can say why it was put there. In code the fence is the weird branch, the extra validation, the delay nobody can explain, the flag nobody remembers — and the reason is rarely in a comment; it lives in an incident, a customer escalation, or a five-year-old commit message. Changing what you do not understand is not refactoring; it is guessing with production traffic.

## When to use

- Touching legacy code with unclear invariants.
- Reviewing deletion and "cleanup" PRs.
- Infrastructure changes: security groups, cron schedules, retry loops, timeouts.
- Repurposing old names — flags, config keys, status codes, endpoints.

## When NOT to use

- When the fence is provably a leftover: verified dead code with no callers, no references in configs or docs, and a history showing why it died — delete it (see YAGNI).
- When the behavior is captured by an executable test that documents the invariant — the reason now lives in the suite, not in oral history.
- Greenfield code you wrote yourself, before anyone depends on it.

## Anti-pattern

- "This looks dead, deleting." as the entire PR description.
- Repurposing an existing flag for new behavior because the name is close enough.
- Removing a validation "because it rejects our new valid input" without finding the bad input it was rejecting.
- Big-bang cleanup PRs deleting fifty unexplained things in one diff.
- Mixing a cleanup into an unrelated feature change, so neither can be reverted alone.

## Code example

Wrong — removing the fence by looks:

```ts
// PR title: "cleanup: remove pointless delay in order submit"
async function submit(order: Order) {
  return api.submit(order); // delay removed — nobody knew what it was for
}
```

Right — find the reason first, then decide:

```ts
// The delay sheds load from a downstream queue that drops bursts
// (incident 2021-04, now documented in ADR-114).
// Keep it until the queue fix ships; remove BOTH together.
async function submit(order: Order) {
  await delay(1500);
  return api.submit(order);
}
```

## Technical enforcement

<Enforcement>
Fences are cheap to respect when process demands evidence:

- **Deletion evidence rule**: PRs that delete code must link their proof — git blame summary, no-caller evidence from static analysis (knip, vulture), or the incident that introduced the code. "Looks dead" is not evidence.
- **Quarantine before delete**: prefer disable-behind-a-flag plus a monitoring window over hard deletion, expand-contract style, so the removal itself is revertable.
- **Staged rollout with auto-rollback**: deploy deletion changes canary-first with alerting on the affected path (see Blast Radius, Observability First).
- **Review checklist**: the reviewer must be able to answer "why did this exist?" — if neither author nor reviewer can, the deletion waits.
</Enforcement>

## Real-world case

<RealCase>
On 1 August 2012, Knight Capital deployed new code for its Retail Liquidity Program. The new code repurposed an old feature flag that had once activated a deactivated "Power Peg" order function — code that had been left on servers rather than removed. The deployment reached only seven of eight servers. When markets opened, orders carrying the repurposed flag triggered the dormant Power Peg code on the missed server — a safeguard that had once bounded it had been retired years earlier — and it pumped erroneous orders into the market for the better part of an hour. Knight lost more than USD 460 million and survived only through acquisition. A verified deployment would have reduced that day's damage; not reusing a flag whose old meaning was still live in production would have removed the failure mode. SEC order: https://www.sec.gov/litigation/admin/2013/34-70694.pdf (verification: ok for the incident and the order; perlu for exact figures — read the order before quoting precise numbers).
</RealCase>

## Tension and trade-off

- **Fence-keeping vs code hygiene**: dead code is a real liability — bit-rot, review cost, false confidence. The rule is not "never delete"; it is "understand, then delete." Verified-dead code should go (see YAGNI).
- **Fence-hunting vs velocity**: waiting for the one engineer who knows a subsystem costs days. Mitigate with small, revertable deletions under monitoring rather than big-bang removal — or ship the removal behind a flag first.
- **Oral history vs codified knowledge**: a fence whose reason lives in one person's memory is already failing. The durable fix is moving the reason into tests, ADRs, and runbooks — making the intent observable, not just the behavior.
