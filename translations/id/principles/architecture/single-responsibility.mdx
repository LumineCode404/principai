<AIInstruction>
Jaga setiap modul, service, dan komponen agar hanya punya satu alasan untuk berubah. Saat hendak menambahkan logic database, email, atau PDF ke sebuah utility class bersama, berhenti dan buat modul yang fokus sebagai gantinya. Saat review, tanyakan peran tunggal mana yang akan meminta perubahan ini — jika beberapa peran yang tidak terkait sama sekali akan memintanya, pecahkan kodenya sebelum merge.
</AIInstruction>

<Severity level="important" />

## Definisi

Sebuah modul punya satu responsibility ketika tepat satu kekuatan — satu tim, satu aturan bisnis, satu jenis perubahan — yang akan pernah menuntut modifikasinya. Responsibility itu soal alasan untuk berubah, bukan jumlah baris kode. Begitu perubahan yang tidak terkait mengalir lewat file yang sama, setiap release menggandeng tim, test, dan mode kegagalan yang tidak ada hubungannya satu sama lain.

## Kapan pakai

- Merancang boundary service dan modul, terutama shared library yang dikonsumsi tim lain.
- Memutuskan ke mana kode baru seharusnya berada — "apakah ini cocok di sini?" adalah pertanyaan Single Responsibility.
- Menyadari bahwa file yang sama terus berubah karena alasan yang tidak terkait, dari sprint ke sprint.
- Memecah monolith: potong di sepanjang seam responsibility, bukan di lapisan teknis.

## Kapan TIDAK pakai

- Skrip sekali-jalan dan tool kecil di mana dekomposisi hanya menambah indirection tanpa menambah keamanan.
- Prototype tahap awal yang responsibility-nya masih dalam proses ditemukan — pecahkan setelah stabil.
- Lapisan orchestration yang responsibility tunggal sejatinya memang mengoordinasikan beberapa langkah.
- Inner loop performance-critical yang sudah diukur, di mana satu indirection ekstra punya biaya nyata yang terbukti.

## Anti-pattern

- Class `Utils`, `Common`, atau `Manager` yang menampung sisa-sisa semua tim.
- Fungsi service yang me-render PDF, menulis ke database, dan mengirim email.
- "Satu helper lagi saja" di komponen bersama, sampai perubahan semua tim saling bentrok.
- Komponen UI yang men-fetch data, mentransformasikannya, lalu me-render-nya — tiga alasan berubah dalam satu file.

## Contoh kode

Salah — satu modul, tiga alasan berubah (layout, persistence, delivery):

```ts
// utils.ts — designer, DBA, dan ops sama-sama membongkar file ini
export class Utils {
  static async invoice(order: Order) {
    const pdf = renderInvoice(order);          // designer mengubah bagian ini
    await db.orders.insert(order.audit);       // DBA mengubah bagian ini
    await smtp.send(invoiceMail(order, pdf));  // ops mengubah bagian ini
  }
}
```

Benar — satu alasan berubah per modul, dirangkai oleh pemanggilnya:

```ts
// billing/invoice-pdf.ts — berubah hanya saat layout berubah
export const renderInvoice = (o: Order) => pdf.build(layoutFor(o));
// billing/order-store.ts — berubah hanya saat persistence berubah
export const saveOrder = (o: Order) => db.orders.insert(o.audit);
// notify/mailer.ts — berubah hanya saat delivery berubah
export const sendInvoiceMail = (o: Order, p: Pdf) => smtp.send(invoiceMail(o, p));
```

## Penegakan teknis

<Enforcement>
Prinsip ini ditegakkan oleh boundary, bukan oleh niat:

- **Aturan import boundary di CI** (dependency-cruiser, eslint-plugin-boundaries): deklarasikan apa saja yang boleh di-import tiap folder; utility bersama tidak boleh meng-import infrastructure.
- **CODEOWNERS**: satu tim pemilik per modul — PR yang menyentuh modul dua pemilik adalah sinyal otomatis untuk memecah.
- **Gerbang ukuran dan cohesion**: batas lint atas panjang file dan simbol yang di-export berperan sebagai detektor smell, bukan hukum keras.
- **Pertanyaan review**: "siapa yang akan meminta perubahan ini?" — lebih dari satu jawaban berarti lebih dari satu responsibility.
</Enforcement>

## Kasus nyata

<RealCase>
Sebuah tim invoicing mempertahankan class `Utils` bersama "untuk menghindari debat soal struktur". Selama dua tahun ia menumpuk PDF rendering, pembulatan pajak, akses database, dan SMTP client. Setiap release train menunggunya: marketing mengubah layout, finance mengubah pembulatan, ops mengubah mail relay — semua dalam satu file, semua saling bentrok. Sebuah hotfix pembulatan pernah ter-ship membawa perubahan PDF yang tidak diinginkan karena keduanya hidup dalam fungsi yang sama. Pemecahan yang lebih awal tidak akan menghentikan setiap insiden, tetapi akan mengurangi setiap insiden menjadi revert satu tim satu file. (ilustratif — komposit dari mode kegagalan yang umum; verification: perlu)
</RealCase>

## Tensi dan trade-off

- **Single Responsibility vs. KISS**: setiap pemecahan memakan file dan indirection. Pecah saat alasan kedua untuk berubah benar-benar tiba, bukan secara preventif untuk masa depan yang dibayangkan.
- **Single Responsibility vs. DRY Tension**: deduplication menarik kode yang serupa ke tempat yang sama; prinsip ini mendorong alasan yang berbeda untuk saling menjauh. Ekstrak kode bersama hanya ketika kedua salinannya akan berubah karena alasan yang sama.
- **Memecah vs. koherensi**: memotong melewati titik context bersama mencerai-beraikan satu ide ke banyak file. Sebuah modul seharusnya sekecil responsibility-nya — dan tidak lebih kecil.

## Prinsip terkait

- [Dependency Inversion](/id/docs/principles/architecture/dependency-inversion) — pisahkan policy dari infrastructure agar responsibility tetap bersih.
- [Gall's Law](/id/docs/principles/architecture/gall-law) — responsibility ditemukan di kode yang berjalan, bukan dirancang di muka.
- [KISS](/id/docs/principles/design/kiss) — timbang setiap pemecahan terhadap indirection yang ditambahkannya.
- [DRY Tension](/id/docs/principles/design/dry-tension) — duplikasi lintas alasan lebih baik daripada unifikasi palsu.
- [Least Astonishment](/id/docs/principles/design/least-astonishment) — satu rumah yang bisa diprediksi untuk setiap perilaku.
