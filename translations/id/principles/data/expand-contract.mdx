<AIInstruction>
Jangan pernah menyampaikan perubahan schema atau interface dalam satu langkah breaking. Tambahkan struktur baru di samping yang lama, migrasikan data dan reader secara bertahap, dan hapus path lama hanya ketika usage telemetry membuktikan tak ada yang membacanya — setiap state antara harus tetap hidup dengan versi campuran yang berjalan. Jika sebuah migration akan me-drop, me-rename, atau mengubah peran sesuatu yang mungkin masih dibaca kode lain, berhenti dan verifikasi consumer-nya lebih dulu.
</AIInstruction>

<Severity level="important" />

## Definisi

Expand-contract (parallel change) memecah sebuah perubahan breaking menjadi tiga fase yang kompatibel: expand (tambahkan struktur baru tanpa menghapus yang lama), migrate (backfill, dual-write, dan alihkan reader), dan contract (hapus yang lama hanya ketika usage telemetry menunjukkan nol reader). Setiap deploy antara harus aman dibiarkan berjalan berjam-jam, karena rollout itu bertahap dan rollback menuju kode lama, bukan maju.

## Kapan pakai

- Perubahan schema pada tabel dengan trafik live: tambah kolom, backfill, alihkan, lalu drop.
- Rename atau perubahan peran field API — field lama dan baru disajikan berdampingan lintas versi contract.
- Migration storage dan format pesan dengan producer dan consumer yang sedang berjalan (in-flight).
- Sistem apa pun yang deploy-nya tidak atomik dan beberapa versi aplikasi berjalan bersamaan — yang merupakan kondisi normal.

## Kapan TIDAK pakai

- Sistem pra-rilis tanpa consumer dan tanpa data — migrasikan satu langkah dan biarkan history-nya sederhana.
- Tabel yang cukup kecil untuk dibangun ulang secara atomik di dalam satu transaksi maintenance window, dengan downtime yang memang sudah dijadwalkan.
- Ketika path lama justru menjadi beban security (membocorkan secret, mengekspos data privat) — rancang penghapusan yang cepat dan eksplisit disertai kompensasi, alih-alih migration yang lambat.

## Anti-pattern

- Satu migration, satu deploy: DROP kolom lama dan ADD kolom baru di release yang sama dengan saat aplikasi mulai memakainya.
- Menambahkan kolom NOT NULL dengan default ke tabel panas di deploy yang sama yang menulisnya.
- Dual-write tanpa reconciliation job — kedua path drift diam-diam dan tak ada yang menyadarinya.
- "Tidak ada yang membaca field lama" diverifikasi dengan bertanya ke tim paling lantang, bukan dengan memeriksa trafik.

## Contoh kode

Salah — satu langkah, atomik dalam arti yang terburuk:

```sql
-- Kode lama (masih berjalan selama rollout) me-SELECT legacy_total di mana-mana
ALTER TABLE orders DROP COLUMN legacy_total, ADD COLUMN total_cents BIGINT;
```

Benar — tiga fase yang kompatibel:

```sql
-- Fase 1 (expand): hanya additive, nullable, tanpa drama exclusive lock
ALTER TABLE orders ADD COLUMN total_cents BIGINT;

-- Fase 2 (migrate): backfill per batch; aplikasi dual-write keduanya dan merekonsiliasi
UPDATE orders SET total_cents = legacy_total * 100
 WHERE total_cents IS NULL AND id % 64 = 0;

-- Fase 3 (contract): hanya setelah log usage menunjukkan nol pembacaan legacy_total
ALTER TABLE orders DROP COLUMN legacy_total;
```

## Penegakan teknis

<Enforcement>
Fase-fasenya ditegakkan oleh tooling yang menolak membiarkan manusia memampatkannya:

- **Migration linter di CI**: DDL destruktif (DROP COLUMN, RENAME, penyempitan tipe) tidak boleh ship di release yang sama dengan perubahan additifnya; pemisahannya wajib.
- **Penjaga lock**: migration berjalan di bawah timeout lock dan statement; migration yang akan mengambil exclusive lock lama di tabel panas ditolak.
- **Usage telemetry sebelum contract**: jumlah pembacaan per field dan per consumer ditampilkan di dashboard; drop hanya diizinkan setelah nol selama satu siklus rollout penuh.
- **Reconciliation job**: selama dual-write, diff terjadwal antara path lama dan baru memberi alert saat drift — drift adalah bug, bukan kenop tuning.
- **Urutan deploy terpisah**: migration dan release aplikasi adalah pipeline terpisah dengan rencana rollback terpisah.
</Enforcement>

## Tensi dan trade-off

- **Expand-Contract vs. kecepatan**: tiga fase berbiaya perencanaan dan koordinasi; migration satu langkah hanya dapat diterima ketika setiap reader berada di bawah kendali dan tabelnya cold.
- **Expand-Contract vs. kejelasan**: path ganda menggandakan permukaan schema dan kode; fase contract adalah komitmen, bukan opsi — jadwalkan, atau ekspansinya menjadi utang permanen.
- **Ditimbang terhadap YAGNI / KISS**: untuk perubahan yang backward compatible secara trivial (additive, nullable, tak dipakai di tempat lain), migration lurus adalah pilihan benar yang lebih sederhana.
